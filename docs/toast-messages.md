# Toast messages

Companion to CLAUDE.md § Design system (v2). Why a toast once rendered as a blank card stretched to ~2.4× its height, what `ToastController.show` now normalizes, and what that means for code that produces a toast.

## Toast strings are normalized centrally

**Toast strings are normalized centrally — don't hand-guard them.** `ToastController.show` (`lib/ui/core/widgets/toast_controller.dart`) collapses the message to a single trimmed line, keeps at most `kToastDetailMaxLines` non-blank detail lines, drops a blank-labelled action, promotes the detail into the title when the message is blank, and **queues nothing at all** when there's nothing renderable (returning `null`, plus a debug-only `Logger` warning with a stack trace so the producer shows up in the diagnostics log). That's the fix for a class of bug where a raw server string — `ApiException.message` is non-nullable, so `{"message":""}` arrives blank, and `ApiClient._raiseFromResponse` splices 240 raw bytes of a 5xx HTML page into it — painted a blank card stretched to ~2.4× normal height (`IntrinsicHeight` sizes the card to its text, and blank lines occupy full line boxes). Consequences for new code: **never rely on newlines in a toast *title*** (use `' · '` to join, as `import_export_screen._msg` does); don't add local `message.isEmpty ? … : …` guards — `Notify.error` / `Notify.warning` already fall back to `tr('an_error_occurred')`; and note the context-free path (`Notify.capture` → `toasts?.error(...)`) has **no** such fallback, so a captured-controller caller must pass a `tr()`-derived string, never a raw server one.

## A bottom toast is lifted above pinned actions

**A toast never covers actions pinned to the bottom of a screen.** On a phone the toast sits at the bottom, which is exactly where a checkout pins its one button — on an iPhone the Tap to Pay on iPhone button, which App Review (5.3) wants never obscured; the unseen-decline notice landed on top of it. `ToastBottomInset` wraps the pinned actions (`CollectStageLayout` does it for every in-person payment stage) and reports its height to `ToastController.setBottomInset`; `ToastHost` adds the reported heights to the narrow layout's `bottom`. Every bar a screen pins to its bottom edge goes through it — the billing editors' sticky totals (both layouts), the list selection bar (`_publishedBottomBar`) and the phone's timer dock — and the **wide** shell reads the same notifier to lift the floating timer pill (`runningTimerPillBottom(bottomBar:)`), which used to sit on a desktop invoice editor's Total; `running_timer_pill_wiring_test` pins all four sites. Five details keep it honest:

- It reports **after the frame** (the height isn't known during build, and a notifier poked during build throws in a sibling `ListenableBuilder`), and gives the height up from `dispose` — mid-frame, so `ToastController.setBottomInset` publishes the sum after the frame whenever it is called in `persistentCallbacks`: the shell's timer pill listens and calls `setState`, which threw "tree was locked" when the notifier fired from inside the unmount (`toast_bottom_inset_test` "unmounting a bar never notifies while the tree is locked").
- It reports **only while its route is on top** (`ModalRoute.isCurrent`): a dialog or another screen over it gets its toast at the ordinary bottom.
- `bottomInset` is a notifier of its own, so a change never rebuilds anything that listens for toasts. The wide (top-end) layout ignores it.
- The reports are **summed**, not maxed: the bars stack (a billing editor's totals sit on the phone's timer dock), so the tallest alone would leave the toast over the upper one. Two side-by-side reporters (a selection bar beside an editor pane) over-lift — harmless.
- It reports only while its subtree's `TickerMode` is on: the shell keeps every branch's stack mounted under `TickerMode(enabled: false)`, so an editor left open on another tab would otherwise go on lifting everything. And a bar that pays the bottom safe inset itself (a `SafeArea`) passes `paysBottomPadding: true`, so the inset the host already adds is not counted twice.

The phone's running-timer dock (`RunningTimerDock`) wraps only its 48-px row, never the safe inset it pays beneath it, because the narrow host already adds `padding.bottom` — wrapping the whole box would lift the toast by the inset twice. Its route is the shell's, so a dialog on the root navigator drops the toast back to the ordinary bottom while it is up.

`collect_fallback_screen_test` ("a toast never covers the pinned actions") pins it. `running_timer_dock_test` ("a bottom toast is lifted above the bar") pins the dock, and `toast_bottom_inset_test` the sum, the inset deduction and the hidden-branch gate. In a widget test a toast's card grows in from a post-frame start: pump once to start it and once more to finish it before measuring.
