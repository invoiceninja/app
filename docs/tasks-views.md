# Tasks layout views

Companion to CLAUDE.md § Tasks layout view. The main file carries the `?view=` / device-preference precedence rule and the rule for each behaviour; this doc carries the evidence — why the URL is an override rather than the carrier, what the lock exists for, and why the kanban board has no create FAB — plus how a task status resolves to a colour.

## Why the URL alone could not carry the layout

Before invoiceninja/flutter#133 the URL was the only carrier, and since every structural "up" navigation drops the query string by construction, the mode was lost the moment the user tapped the FAB: `goToCreateRoute` `go`s a bare `/tasks/new`, `MasterDetailLayout` auto-promotes that to `?view=full`, and `entityCloseTargetPath` returns the bare `basePath` — so cancelling a new task landed on the plain list. Three sibling paths lost it too (closing a card's detail pane, re-tapping the already-active Tasks sidebar row, a company switch made from `/tasks/<id>`); Android back and the sidebar `←` never did, because `NavHistoryController` records the full URL. Hence `DevicePrefKeys.tasksView` as the fallback, with `?view=` kept as the override.

## The `view` key is overloaded, so `full` must parse to null

**The `view` key is overloaded, so `'full'` must parse to null.** `MasterDetailLayout` writes `?view=full` for its full-width pane flag (`_toggleFullScreenInUrl`, plus the auto-promote redirect a frame after an editor opens) and the tasks list is rebuilt from that same `GoRouterState` — so every open editor hands the parser `'full'`. Null means "the URL expressed no opinion"; mapping it to `list` would claim the URL had chosen the list. Every *other* reader of `queryParameters['view']` in `lib/` compares against `'full'`, so the overload stays contained to one line. This is also why the mode is **not** carried on the pane URL instead: `_toggleFullScreenInUrl` would clobber it going in and strip it coming out.

## The fallback is suppressed when the screen can only be the list

**The fallback is suppressed whenever the screen can only be the plain list** (`locked`), and each arm exists for something that fails silently. **A pane is open** (every view but the board, which stays behind its pane — § The board is a whole view) — only `EntityListScreenScaffold` writes `MasterDetailNavController.update`, and the pane reads it for J/K row-stepping and for `EntityDetailScaffold`'s synchronous first-frame seed, so a board behind the pane kills both and opens the detail on a spinner; `_SelectedIdScope` is inert there too, and `TaskCalendarScreen.initState` does network I/O (`loadStatus` + the events fetch), so a remembered calendar would fire a connection-status request on **every record opened**. Locking keeps everything behind the pane identical to what shipped — the mode only has to survive the trip *out*. **A `ListFilterIntent` rode in** on the route's `extra` (a dashboard task card) — only `GenericListViewModel` consumes it, so a board would swallow the drill-down. **Embedded, or scoped to a client / project** — the board and calendar take no such argument and would drop the filter.

## The toggle emits no `?view=` — a view switch is not a history step

**The toggle emits no `?view=` at all — a view switch is not a history step.** `TasksViewToggle._go` writes `Services.tasksView` and navigates to a bare `/tasks`. It has to be that way round: `isUpNavigation` compares paths only, so `/tasks` and `/tasks?view=kanban` are separate history entries, and pressing Android back onto the bare one re-renders the board from the preference — the press changes nothing on screen and reads as a broken back. Every other list-view control in the app (filters, sort, status tabs) already lives in `nav_state` and creates no entry; this now matches, and the URL stays a pure override for the paths that genuinely carry one. The cost is that the `go` is a **no-op whenever the URL is already `/tasks`** — `GoRouterDelegate.setNewRoutePath` returns early on an unchanged `RouteMatchList`, so `NavStatePersister` and `NavHistoryController` see nothing either — which is exactly why the `ValueListenableBuilder` in § `_RememberedTasksView` is the second writer below is the entire repaint path and must not be made conditional. `_go`'s early return needs **both** halves (`next == active` AND the stored value matching): `active` is what the screen renders, and a locked screen renders List even for a Kanban user, so tapping List there must still be able to set it.

## `_RememberedTasksView` is the second writer, and its builder is unconditional

**`_RememberedTasksView` is the second writer, it writes post-frame, and its `ValueListenableBuilder` is unconditional.** The toggle writes the user's own choice; this mirror covers every URL-driven path — the calendar day-cell's `?view=daily&date=…`, the post-OAuth `/tasks?view=calendar`, a restored `nav_state` route, back/forward — so the preference cannot drift from a URL that does name a layout. Post-frame because `ValueNotifier.notifyListeners` must never fire inside the parent's build phase. **Do not wrap the builder in an `if (locked) return …`**, however tempting: `locked` carries `hasPane`, which flips on every pane open and close, so the widget at the list's slot would alternate between `ValueListenableBuilder` and `EntityListScreenScaffold`, `Widget.canUpdate` would fail on the runtimeType change, and the list would be unmounted and re-inflated. The wide branch of `MasterDetailLayout` keeps that element alive on purpose (`Positioned.fill(Offstage(…))` is Stack child 0 in both pane states), so the symptom is a desktop list that resets its scroll, rebuilds its ViewModel back to page 1 and drops multi-select every time a row is clicked — and a re-seeded `MasterDetailNavController` that can no longer resolve the row the pane just opened. Narrow remounts anyway, so it is invisible where it is easiest to test. `EntityListScreenScaffold._statusTabs` is **not** a precedent for branching here: that guard wraps an optional *sibling* in a `Column`. `test/lint/tasks_view_wiring_test.dart` fails the build on the early return.

## `stripTransientQuery`'s carve-out for a non-`full` view must stay

**`stripTransientQuery`'s carve-out for a non-`full` `view` must stay** even though the toggle no longer produces one: the calendar day-cell link and the post-OAuth landing still do, and stripping it would drop the layout from a restored route for exactly those. (It is **not** what keeps Android back working — the toggle emitting no `?view=` is.) Three known gaps, deliberately not fixed here: applying a Tasks **saved view** while a board is showing does nothing visible (its filters land in `nav_state.filters_json`, which only `TaskListViewModel` hydrates), `/tasks?client_id=…` still loses its filter through a pane round trip, and a dashboard card's `ListFilterIntent` lock lasts only as long as the route entry that carried the `extra`, so opening one of the drilled-into tasks and closing the pane unlocks the screen and a remembered board replaces the filtered list (the filters survive in the VM and `nav_state`, and every task card ships `{}` filters today, so nothing is actually lost yet) — the general cure for that is a "sticky list query" concept in the entity-agnostic navigation helpers, which is a much wider change than a bug fix wants.

## A kanban card says who it is for, and drags whole

**A kanban card is the title, then who it is for, then a corner of time · assignee · timer — each present only when it has something to say — and it drags whole: at once with a mouse, on a long press under a finger, with the board scrolling itself at its edges.** That is invoiceninja/app#195 (the card named the client but never the project) plus the review it prompted, measured against Linear, Trello, Jira, GitHub Projects, Notion, Toggl Plan and Everhour.

- **Client and project are separate lines, told apart by an icon** (`person_outline`, `work_outline` — the project module's own). Joined on one line of a 300 px card each name is cut to half; as two identical muted lines nobody can tell which is which, and a project is not always named after its client.
- **No `0:00`.** A task nobody has worked on or booked leaves the time slot empty. A booked-but-unstarted task still shows *when* (`taskScheduleSlot`), a running one its ticking timer and an accent border — the accent is reserved for running, which is why invoiced uses `tokens.paid`. (`watchAllByStatus` drops invoiced tasks, so the board never draws that branch today; it is kept for the drag ghost and any future "show invoiced" switch.)
- **The assignee and the timer sit in the bottom-end corner, beside the lines under the title, not on a row of their own.** A row holding only a play button cost every untouched card a third of its height — four cards filled a 620 px column. The lines under the title give up the corner's width; the title never does, and `_cornerClearance` holds it clear when there is only one line (or none) beneath it. An unassigned task draws no avatar at all: a board of placeholder badges is noise.
- **The card has no drag handle.** The handle sat over the end of the title (a long title ran under it) and made a 26 px target of the board's main gesture. A mouse drag scrolls nothing, so `Draggable` starts at once and a click still opens the task; under a finger a plain vertical drag is the column's scroll and a horizontal one the board's, so touch takes `LongPressDraggable` — gated on `Env.isTouchPrimary`, the same split the invoice designer's canvas makes. The **column header keeps its handle**: reordering statuses is rare, and a header that moved under any drag would be a trap.
- **A drag cannot scroll a list, so the board does it** (`_onCardDragUpdate`): within 56 px of either side it scrolls towards that side, faster nearer the edge. Without it a card could reach only the columns already on screen — on a phone, its own, which made the board read-only there in practice. Vertical edge-scroll inside one long column is **not** built.
- **A phone shows one column and 28 px of the next, and comes to rest on a column** (`_ColumnSnapPhysics`, `PageScrollPhysics` with a column-plus-gap page). A snapping board pulls every small scroll step back to its boundary, so under a drag it turns **one whole column at a time**, pausing 700 ms on each — long enough to drop there.
- **The side padding is the list's, not a box around it**, so columns scroll out under the pane's edge instead of being cut 24 px short of it.
- **The header reads `name · count … total`**, the total being time worked across the column's cards (`_ColumnTotal`) — on a billing board "what is this status worth" is the question a count cannot answer. Nothing for a column with no time; it re-reads once a minute while a card's timer runs. A status with no name reads `(no name)`, never its hashid.

`kanban_card_test.dart`, `kanban_column_test.dart` and `kanban_board_test.dart` pin all of it; `kanban_behind_pane_test.dart` drives a real `GoRouter` + `MasterDetailLayout` + `TaskListScreen` to prove the same board `State` survives a task opening over it, and `kanban_screen_test.dart` the Display menu on the real screen.

## The board is a whole view: it loads itself, moves cards without a drag, and stays behind an open task

**The board syncs the task table when it opens, computes every move on the unfiltered columns, offers each move from a menu as well as a drag, and stays mounted behind a task pane — the one Tasks view that does.** Each was a way the board fell short of the tools it is measured against; none failed loudly.

- **It loads its own data.** `KanbanViewModel` reads Drift and nothing else, and lists load a page at a time, so the board showed only the tasks some other screen had happened to fetch — a user whose remembered view is the board opened a partial one on a fresh install. It now calls `TaskRepository.refreshAll` once per mount: the Sync pass's own sweep for this table, so the first call pages everything and every later one is the delta behind the cursor. The board draws what the device holds at once; the sync shows as a 2 px bar (`isSyncing`), never a spinner over it. Offline it simply fails, and what is cached is the board.
- **A filter no longer switches drag off.** It used to (`canEdit && !filtersActive`), because a reorder built from the visible cards dropped every hidden one from its status's persisted order — and nothing said why the cards stopped moving. `moveTask` builds the layout from the UNFILTERED columns and places the card relative to one that is really there, so hidden cards keep their places. `commitReorder` is `@visibleForTesting`: it takes the full layout, and a caller that hands it a filtered one reintroduces the bug. `tasks_view_wiring_test` fails if `kanban_board.dart` mentions `filtersActive` again.
- **A task on no column gets one.** A blank `status_id` (a task created offline before the server assigns its first status) or the id of a deleted status matched no column, so the task was in the board's data and nowhere on it. `KanbanViewModel.noStatusId` is a leading `No status` column, drawn only while it holds something. It is not a status: cards drag OUT of it, nothing drops in, and it has no create footer and no fold.
- **Every move is a menu item too.** The card's `⋮` (always drawn: hover-only would hide it from touch; 44 px under a finger, the touch floor, 28 with a pointer — the extra height comes out of the air above it, so a touch card grows by 4 px, not 8) opens `Move to ▸ <status>` followed by the task's own actions (`TaskActions.itemsFor` — the same list the record and the list row show). A menu move lands at the TOP of the column, where the user sees it arrive; there is no position to point at. The same moves are `customSemanticsActions` on the card, because a screen reader cannot drag at all.
- **The board stays behind its pane.** Opening a card used to swap the board for the list (`locked` carried `hasPane`), so reading one task cost the user their place. `resolveTasksViewMode` now takes `hasPane` apart from `locked` and exempts kanban — and only kanban, because only it meets what the pane asks of the screen behind it: `KanbanBoard` writes `MasterDetailNavController.update` itself (ids in board order, so `J` / `K` step card to card; the tasks, so the pane seeds its first frame instead of opening on a spinner) and does no I/O per record opened. The open card draws selected; tapping it again closes the pane, as a list row does. Calendar, daily and weekly are still locked for the reasons in § The fallback is suppressed whenever the screen can only be the plain list.
- **A column folds to a 44 px strip** (`KanbanCollapsedColumn`: colour, count, the name down its length) that still takes a drop and opens on a tap. A phone goes on snapping: `_ColumnSnapPhysics` takes the columns' own start offsets as its stops, not a fixed stride, because a strip is not a column wide.
- **An empty column says `No tasks`, and nothing more** (`kanban_column_empty`). The same column is Backlog, Done or a status the company named itself, and under a filter or a search "empty" may only mean "nothing matches", so a per-status promise ("Start a timer to begin", the design's) would be wrong in most of them. The line sits inside the column's drop target, which still fills the column.
- **`+ New Task` is a field, not a trip to a form.** A tap turns the footer into one: type a title, Enter, and the card is at the bottom of the column with the field still open for the next (`_CreateFooter` → `KanbanViewModel.quickAdd` → `TaskRepository.create`, so it queues offline like any create). Escape, or leaving it empty, puts the button back; leaving it with text keeps the text. The full form is the button beside the field. **A quick-add takes the active filters** — client, assignee, and a project's own client and rate — because a card added to a filtered board that then vanished behind that very filter would read as a failed create. It is still the `create_task` gate and nothing else (`canCreate`), and the lanes layout keeps the header `+` to the full form: a lane cell has no room for a field per cell.
- **Lanes are a second axis** (`Display ▸ Group by` client / project / assignee): one row of column headers, then a lane per group, each a row of cells under those headers. The sheet scrolls sideways as one, the lanes vertically under fixed headers, and a lane's title is pinned to the viewport's start edge (`_PinnedStart`) so a phone's second column still says whose cards it shows. Named lanes sort by name, the "none" lane last. **A card changes status inside its own lane only** — dropping it in another lane would have to rewrite its client, project or assignee, and a status board is the wrong place to do that by accident. Folded lanes are remembered (`KanbanPrefs.closedLanes`, keyed `<grouping>:<id>` so a client folded as a client lane is not folded as anything else). In lanes a column has no footer, so its `+` moves into the header.
- **A long column, and the lanes, scroll under a held card** — `KanbanDragScroller` ticks while a drag lasts and each scrollable that should follow the pointer listens to it.
- **What a card shows is the user's** (`Display ▸ Card fields`): client, project, assignee, duration, and the task number, which starts off. All of it — fields, grouping, folded columns — is one `KanbanPrefs` JSON blob under `DevicePrefKeys.kanban` (account scope: the folded set names this account's statuses). Fields are stored as their DIFFERENCE from the defaults, so a field a later build adds arrives at its default rather than reading as switched off.

Still not built: multi-select, keyboard shortcuts on a focused card beyond `J` / `K` behind a pane, WIP limits, and a time window on the last column (the board already leaves invoiced tasks off).

## The kanban board is the one Tasks view with no create FAB

**The kanban board is the one Tasks view with no create FAB, and the gate that makes that safe is not the one it looks like.** Daily / weekly / calendar each build the same `FloatingActionButton` (hidden from a user without `create_task`); kanban had a fourth copy, and it was the redundant one — every column ends in a `+ New Task` that seeds *that column's* `status_id`, while the FAB seeded nothing. `emptyTask()` is `statusId: ''` and `watchAllByStatus` groups strictly on that key, so a FAB-created task **whose status the user left blank** — the form has a picker, but nothing defaults it — sits in no column until the server's `TaskRepository::setDefaultStatus` assigns the first status on the round trip, i.e. never, offline. On a phone `endFloat` also parked it on top of the footer of whichever column was scrolled to the right edge. That was invoiceninja/flutter#135, and React had already settled it: `Kanban.tsx` has no page-level create control at all, only a per-column `+` gated on `hasPermission('create_task')`. **The trap is what that footer was gated on.** `KanbanBoard` used to pass `canEdit && !vm.filtersActive` to stop a reorder computed from a filtered, partial set (since replaced — § The board is a whole view), and the footer was riding along, so applying any Client / Project / Assignee filter took away the board's *only* remaining create path. `canCreate` is now a separate parameter carrying `create_task`, and it is deliberately filter-independent: a quick-add writes one task's `status_id` and rewrites no order. The token matters as much as the split — `edit ⇒ view` and `delete ⇒ edit` are the **only** cross-verb implications `can()` makes (it also expands `<verb>_all`, and admin / owner short-circuits the lot), so an edit-only user genuinely cannot create, and a create-only one previously had the FAB and no footer. Two things are deliberately left alone: the `statuses.isEmpty` empty state keeps its `New task status` CTA and offers no task-create at all (with no columns there is nothing to create *into*, and the other four layouts are one tap away on the same AppBar), and the daily / weekly / calendar FABs stay, because **a FAB may only be dropped where the substitute is the same verb** — which is the rule to carry forward, not "kanban has another button". Daily and weekly are specifically not a precedent: each already shows a `+` FAB *and* a `Log time` button on both widths (`task_daily_header.dart`, `task_weekly_screen.dart`; both withdrawn together from a user without `create_task`), and `TaskDailyActions.logTime` really does create — it ends in the same `goEntityCreateFullWidth('/tasks')` — but it pre-fills a 30-minute `TimeEntry` and is labelled as logging time, so removing their FAB would make a plain new task unreachable from a timesheet view. Calendar's only other create is convert-this-event (`convert_event_to_task_sheet.dart`), which needs a connected calendar and an event to convert. `test/lint/tasks_view_wiring_test.dart` scans for a returning FAB — stripping `//` first, or it trips on the comment in `kanban_screen.dart` that explains the absence — and for the two gates staying apart; `kanban_column_test.dart` pins the widget in both directions, since every failure here is silent: the wrong gate simply draws one widget fewer.

## Task status colours resolve through `taskStatusColors`

**Task status colours resolve through `taskStatusColors`** (`lib/ui/core/utils/task_status_colors.dart`) — the list pill, kanban column dot, settings row dot, and settings live preview all call it; never parse `TaskStatus.color` inline. `''`, `#fff` and `#ffffff` all mean **unset**: the server creates a new company's four statuses with no colour (MySQL default `#fff`) and the API factory writes `''`. Unset + a recognised built-in name (`backlog` / `ready_to_do` / `in_progress` / `done`, matched against the active locale *and* English) maps onto the `draft` / `partial` / `sent` / `paid` token pairs so the defaults read grey / blue / amber / green; anything else unset stays `ink3`. A user-picked hex always wins.

## The layout resolves from `?view=` over a device preference

The Tasks screen has five layouts (list / daily / weekly / calendar / kanban). The layout is **`?view=` on the URL as the override, `DevicePrefKeys.tasksView` as the fallback** — `tasksViewModeFromQuery` + `resolveTasksViewMode` (`lib/domain/tasks/tasks_view_mode.dart`, a leaf that imports nothing so `lib/app/tasks_view_controller.dart` need not import a UI screen; `task_list_screen.dart` re-exports the enum). Why there is a fallback at all: `docs/tasks-views.md` § Why the URL alone could not carry the layout. Five things are load-bearing.

## Seconds are an opt-in device preference read through `watchShowSeconds`, a running timer's day form gains them only where its caller passes `secondsPastDay`, and the editable start / end fields stay minute-grained

Every running timer ticks `H:MM:SS` by default — except the task list's Duration (both widths), which reads `H:MM` (below). A few Tasks surfaces leave seconds out, each for a reason: the kanban cards re-render once a minute (a frozen seconds digit reads as a bug), a duration past a day collapses to `1d 03h 12m`, and a time entry's start and end read as a clock time (`9:30 AM`). Device Settings → Appearance → Lists → **Show Seconds** (`DevicePrefKeys.showSeconds`, device scope, off by default; `ShowSecondsController`) adds them back. Surfaces read it through `watchShowSeconds(context)` (`lib/ui/core/utils/show_seconds.dart`), which is off with no provider, so a widget test that doesn't care needs nothing.

- **`RunningDurationLabel` reads it in `didChangeDependencies`** and, while it is on, ticks every second whatever `precision` its caller asked for. That is what makes the kanban cards' timers carry seconds. The cost is one timer per visible running card, which is why it is opt-in.
- **Its day form gains seconds only where the caller passes `secondsPastDay: true`** — the kanban card, the record screen's Time Log card and the edit screen's narrow time-log rows. The shell's running-timer pill leaves it off: `1d 03h 12m 05s` does not fit it.
- **The task list's Duration is the task's total as hours that run past 24 — `36:30`, never `1d 12h 30m` — with seconds only while Show Seconds is on, and is never cut off** (invoiceninja/flutter#183). Both widths, stopped and running: `RunningDurationLabel(hoursOnly: true)` with the stopped entries as `base` (so starting a timer continues the total rather than resetting it to `0:00`), and `formatDuration(d, showSeconds: watchShowSeconds(context))` for a stopped row. `hoursOnly` keeps the one-second ticker, so the minute rolls over on time; the label repaints only when its text changes. The phone row used to clamp this to 76 px and roll into days, which cut a long total to `1d 12h…` and `13:15:…`; the clamp is gone — the task name is the `Expanded` that gives way — and so is the clamp on a booked clock time (`12:00…` lost its AM / PM). A late booking reads `+26:15`. Not the account's hours-format preference: decimal hours on a live timer (`36.51`, changing every 36 seconds) reads as noise, and a column mixing decimal stopped rows with `H:MM` running ones reads as two units. A total rounds down (`Duration.toString`), so a stopped row can read a minute under the weekly view's rounded `H:MM`.
- **`formatDuration`'s `secondsPastDay` is separate from `showSeconds`.** The duration *fields* (time-entry editor, the create-from-line-item sheet) seed themselves with the compact day form and parse it back, so `compactDays` alone must keep its shape. Only read-only surfaces pass `secondsPastDay`.
- **`formatTimeOfDay(second:)` is passed only by the read-only times** — the record screen's Time Log card, the edit screen's narrow time-log rows, the Daily view's entry rows (whose range is `Flexible`, since a 12-hour range with seconds overflows beside a project name). `InTimeField` holds a `TimeOfDay`, which has no seconds, so the editable start / end fields stay `H:MM`; showing seconds there needs a seconds-aware value first, or a blur that re-commits the field would drop them.
- **Left out deliberately:** estimates, the Booked figure and typed durations (entered in minutes, so seconds would always be `:00`), Daily / weekly totals and report hours (summaries, with their own hours-format preference), and a stopped Daily row's duration (it sums to the Daily header's `H:MM` total).

## The task form's time column leads with the timer, and its figures are the record's

**The task edit form opens its time column with a timer card — the running entry's clock, the one Start / Resume / Stop, and a Logged · Billable · Booked · Estimate strip — whose figures come from `TaskTimeSummary` (`lib/domain/tasks/task_time_summary.dart`), the computation `TaskDetailStanding` uses too.** (`TaskEditTimerCard`, above the time log in `TaskEditTimesSection`.)

- **The clock is the running entry only, and it collapses when nothing runs.** A `0:00:00 · Timer stopped` reads as a figure, and Logged right under it already says what has been worked. While it runs the strip moves under the clock; stopped, the strip is the card's only row, with the button at its end. The clock is a `RunningDurationLabel`, which renders through `LtrText` everywhere now, so a duration keeps its order in a right-to-left layout.
- **The button is the form's only timer control.** The toolbar has none (`TaskEditScreen` filters `isTimerAction`), and it acts on the draft: Start and Resume go through `TaskEditViewModel.startTimer` → `planTaskStart` (`docs/task-scheduling.md`), Resume only while `scheduleState == none`. Hidden on an invoiced task. There is deliberately no task-level Billable switch: billable is per entry, and the table sets it per row.
- **The strip is the record's rules on the draft.** Logged is `loggedDuration` and Billable `billableDuration`, both ticking once a second while the timer runs (the card's own ticker; the `TaskTotalDurationLabel` that used to sit in the time log's header is gone, since it showed the same Logged figure). Billable is left out where `allow_billable_task_items` is off, Booked shows only when something is booked, and the estimate — with an r1 bar of the share used — only when the task has one; an overrun fills the bar and reads `Remaining: -X` in `overdue`, the standing card's wording. Totals follow Show Seconds; the booking and the estimate never carry seconds (they are typed in minutes).
- **No entries: no column headers, the shared empty state** (`TimeLogEmptyState`, built on `EmptyStateBody` because the form already scrolls). An invoiced task keeps the title and loses the line inviting the user to log time. The wide table returns it itself, rather than being swapped out, so its State survives and the first row added still gets its start cell focused.
- **The remove ✕ is one widget, `TimeEntryRemoveButton`, on both layouts** — 44 px under a finger, 32 px with a pointer, pinned per `docs/touch-targets.md` traps 2, 3 and 5; the wide table's remove column is sized from the same number. It had been `VisualDensity.compact` with 32 px constraints, which a touch platform rendered at 40.

- **The wide header's status is the draft's** (`titleTrailingBuilder` in `TaskEditScreen`): a `TaskStatusPill` at the billing documents' pill size, following the Status picker as it changes, and nothing while the status is blank or on create. A billing document shows its *saved* status there because its status is not a field of the form; a task's is.

`test/ui/features/tasks/widgets/edit/task_edit_timer_card_test.dart` pins the card, the empty state and the button sizes; `task_time_summary_and_rate_source_test.dart` the shared computation.

## The view toggle names the view it is showing

**On a wide pane the view toggle labels its active segment and leaves the other four as icons with tooltips; on a narrow one it stays the icon menu.** Five labels do not fit beside the Tasks list's search box, and five bare glyphs (list, day, week, month, board — three of them near-identical rectangles) never said which view the screen was on. It is no longer a `SegmentedButton`: that lays every segment out at the width of the widest, so one label made all five as wide as `Kanban` (~500 px, overflowing the wide AppBar row); `_ViewSegments` gives each segment its own width inside one rounded outline, 36 px tall with a pointer and 44 under a finger. `wide` is the host screen's own `LayoutBuilder` read — `EntityListScreenScaffold`'s for the list, `buildTasksViewAppBar(wide:)` for the other four — never `MediaQuery`, the split § The three time-oriented Tasks headers take the screen's pane bool (`docs/pane-width-and-overflow.md`) settled.

## The wide filter row is one band of labelled dropdowns, and the board alone gets a search

**Where `taskFiltersInline` lets the filters render in the body, they are one 36 px row (44 under a finger) — the board's search, then `Project · Any ▾`, `Client · Any ▾`, `Assigned User · Anyone ▾`, then a `Clear Filters` link while anything narrows the view; narrow panes and phones keep the icon and the chips.** The three labelled pickers it replaces spent ~90 px of band on a label line over a 44 px field. Each dimension is described once (`TaskFilterDimension`, built by `taskFilterDimensions`) and drawn as the sheet's `EntityPickerField` or the row's `TaskFilterDropdown`, so the whole-table option streams, the by-id resolution and the nameless-record fallback cannot drift between the two (`task_filter_bar_wiring_test`). The dropdown keeps `EntityPickerField`'s two selection rules — resolved by id through `watchById`, never by scanning the active-only option list, and sticky on a null — and opens a menu with a search field over the options (type-to-search, CLAUDE.md § Searchable pickers): Enter takes the first match, ↓ moves into the list, and ← / → are handed back to the caret because the menu maps them to focus moves. Each control has a width cap and gives way below it, so the gate's narrowest inline pane (648 px) still holds the whole row.

- **The search is the board's alone** (`TaskFiltersMixin.supportsSearch`, true only on `KanbanViewModel`): the list has its own token search, and daily / weekly / calendar are a few days of rows. Every word must occur in the description, the number, or the client or project name (`matchesSearch` — `fieldsMatchEveryWord`, the rule every list search follows), names read from `watchAllNames` so a task on an archived client is still found by that client's name. It counts as a filter (`filtersActive`, the icon's dot, Clear), and narrow keeps it reachable: the sheet carries the field and the chip strip a `Search` chip, so a search typed on a wide pane is never an invisible filter once the pane narrows.
- **A card quick-added under a search stays on the board until the search changes**, for the reason a quick-add takes the other filters: a card typed into a column that vanished because its title does not match the search would read as a failed create. Keyed on the created row's id, so it lasts until that id is remapped by a sync.

## The time views sit in a white panel

**Daily, Weekly and Calendar draw their rows in the same white panel a standalone entity list does (`ContentPanel`, `lib/ui/core/widgets/content_panel.dart`: `surface`, `border`, `r3`, `shadow1`; `entityListTableInset` on a wide pane, 16 px each side and `InSpacing.md` above and below on a narrow one), and the panel owns the bottom safe inset.** It adds `padding.bottom` to its own bottom margin and hands what it holds `MediaQuery.removePadding(removeBottom: true)` — the list scaffold's `_standalonePanel` rule (`docs/entity-lists.md` § A standalone list sits in a white panel), so nothing inside pays the inset twice. The filter bar and the view header above stay full-width `surface` bands, as the list's app bar and status strip do; the panel is what sits on the page `bg` below them. Four things are load-bearing:

- **Daily keeps its clearance inside the scroll.** `fabScrollClearance(context)` is read *under* the panel's `removePadding`, so it resolves to `kFabClearance + InSpacing.sm` with no inset — the inset is the panel's. The no-`+` branch still passes `null`, never `EdgeInsets.zero`.
- **Weekly's panel ends above the `+`, and hugs the grid.** The totals row is pinned outside the vertical scroll, so the clearance is the panel's whole bottom margin (`ContentPanel(bottom: fabScrollClearance(context))`, measured outside the panel, inset included) — page background under the button, never the grand total. The grid is a fixed `kWeeklyGridWidth` (968 px), so the panel is capped at that plus its border and gutters, start-aligned; on a narrower pane it fills the pane and the grid scrolls sideways inside it. The totals row lost its bottom rule: the panel's border is that edge now.
- **Calendar spends the panel's chrome before the clearance, and only from spare height.** The month grid never scrolls and its cells clip silently (`kTaskCalendarMinGridHeight`). The panel's 2 px of border is unconditional; its top margin is clamped to what is spare above the floor, and `taskCalendarFabClearance` then runs on what is left. A landscape phone, already under the floor, gets neither the margin nor the clearance — the trade it already made before the panel.
- **An empty day or week keeps its bare `EmptyState` on the page**, no panel, as an empty list does. The weekly screen checks `rows.isEmpty` itself (through a `Builder`, since `_body` runs on the State's context above the provider); the empty branch keeps the old padding.

The kanban board has no panel: its lanes are already `surfaceAlt` cards on the page, and a panel around them would be a card holding cards. Pinned in `test/ui/core/widgets/content_panel_test.dart` (margins, the inset, the chrome) and `task_daily_screen_test.dart` (an empty day has no panel).

## The running timer is an inverted bar

**`RunningTimerDock` (phone) and `RunningTimerPill` (railed shell) draw the running task as an inverted bar: `InTheme.inverseSurface` (the theme's `ink`) as the fill, `onInverse` (its `surface`) for the duration and the stop button, `onInverseMuted` for the description, the pulsing accent dot, and the duration in `kMonoFontFamily`** — the one live thing on a screen of white cards, after Hillel's Nov 2026 mockup. The getters are derived from tokens every preset already sets (no new field, no raw colour), so the bar is near-black with light text in the light presets and near-white with dark text in the dark ones. Load-bearing:

- **"Due now" stays distinct on the same fill.** A booked block shows a still dot and a bold "Due now" in `warningOnInverse`, and its Start button takes that colour too, where a running timer's dot is the accent and pulses. `warningOnInverse` is the *other* brightness's `warning`: a theme's own amber is tuned for a surface of the opposite lightness to `ink`, and reads only ~3.5:1 (light) / ~2:1 (dark) on it; the swap gives ~8:1 and 4.3-4.6:1. `test/app/inverse_surface_test.dart` holds all three inks over all six presets.
- **The ripple is the bar's own.** The theme's overlay is ink-on-surface, which paints nothing visible on an ink fill, so both shells pass `overlayColor: _inverseOverlay(tokens)` (`onInverse` at 8 % hover, 14 % pressed / focused). The buttons inside take `color: onInverse`, which derives their overlays.
- **The pill is a rounded rectangle, never a stadium** (`InRadii.r3`, CLAUDE.md § Design system (v2)), with `shadow2` since it floats. The mockup drew a pill; the shape rule wins.
- **The dock lost its top rule** — the fill is the edge. Its geometry (48 px floor, the inset it owns, `ToastBottomInset`, the keyboard hiding it) is unchanged: `docs/sidebar-and-shell.md` § One surface, one safe-area owner — and the owner must be last.

`running_timer_dock_test.dart` pins the fill, the inks, the mono duration and the due-now cue.
