# Web views on Windows, and where the app uses one

Companion to CLAUDE.md § Architecture — at a glance. Which package draws a web view on each platform, why Windows has its own, and the two places the app shows one: the embedded DocuNinja builder and the email previews.

## On Windows the web view is WebView2 through `webview_flutter_windows`, pinned, and every web view surface keeps one set of rules on both packages

`webview_flutter` has no Windows implementation. iOS, Android and macOS use it; Windows uses [`webview_flutter_windows`](https://pub.dev/packages/webview_flutter_windows) (WebView2), behind `lib/ui/core/widgets/windows_web_view.dart`. Linux and the web have no web view the app ships, and fall back.

- **Why this package.** It renders off screen into a Flutter `Texture`, so a dialog, a loading cover or a toast paints over it and it scrolls and clips like any widget. The alternative that implements `webview_flutter`'s interface (`webview_win_floating`) floats a native window over the app: no Flutter widget can draw above it, so the builder's "discard changes?" dialog and its loading cover would sit behind the page, and a preview inside a scrolling pane would not clip. It also hands keyboard focus to the page properly, which the app's shortcut layer depends on (typing in the builder must never fire a `G` jump).
- **It is pinned exactly** (`webview_flutter_windows: 1.3.1`). It is a small fork of `webview_windows` (the original, with the same API, has not been released since 2024); an upgrade is a deliberate, reviewed change, not a `pub upgrade` side effect. It needs WebView2 SDK headers from NuGet at build time, which its CMake fetches with pinned hashes.
- **Its own API**, not `webview_flutter`'s: `WebviewController` / `Webview`, `loadUrl` / `loadStringContent`, `executeScript`, `addScriptToExecuteOnDocumentCreated`, `webMessage` (from `chrome.webview.postMessage`), and `url` / `loadingState` / `onLoadError` streams. It cannot refuse a navigation or name a JavaScript channel, so each surface rebuilds those two (below).
- **A data folder of the app's own.** The plugin's default is a shared `flutter_webview_windows` folder under the user's local app data, named only by the executable, which a sign-out could not clear without guessing at it. `ensureWindowsWebViewEnvironment` points WebView2 at `<application support>/WebView2` once, before the first controller (the plugin keeps that setting when its reference-counted environment is created again).
- **Every controller is counted** (`startWindowsWebView` / `disposeWindowsWebView`), held from the moment it exists so a screen closed during start-up still lets it go, and a sign-out deletes the data folder only while none is open (`windowsWebViewsAlive`): a live browser process holds its files, and a partial delete would corrupt its profile.
- **No runtime, no web view.** WebView2's runtime ships with Windows 11 and comes to Windows 10 with Edge; where it is missing, `startWindowsWebView` returns null (logged once a run): a preview shows what the platforms without a web view show, and the builder its "could not open here" page with the button to the browser. A builder whose WebView2 starts but will not take the page is let go the same way.
- **Not verified on a Windows machine yet.** The Dart side is analysed and tested on the others; CI's `build-windows` job (`ci.yaml`, dispatched by hand) proves it builds. Check on a device: the builder handshake, a file input, typing in a field with the app's shortcuts on, the previews, and a sign-out clearing the data folder.

## The embedded builder keeps the same rules on WebView2: only the web app shows, the page talks over `InvoiceNinjaApp`, nothing it stored outlives the screen

`DnEmbedSurface` (`lib/ui/features/docuninja/widgets/docuninja_embed_surface.dart`) is the builder's web view, with one implementation per package; the screen and its view model do not know which.

- **The channel.** On Windows a script WebView2 runs before the page's own (`addScriptToExecuteOnDocumentCreated`), in the main frame on the web app's origin only, defines `window.InvoiceNinjaApp.postMessage` and forwards to `chrome.webview.postMessage`. React's embed mode looks for that object before it boots, exactly as it finds the `webview_flutter` channel elsewhere. Every message after `init` still has to carry the screen's nonce (docs/docuninja.md).
- **Only the web app shows.** `webview_flutter` refuses a main-frame navigation off the web app. WebView2 cannot, so when the main frame's address leaves the web app it is opened in the browser and the web view goes back. The page that briefly loaded never had the token: it lives in the web app's own session storage, and the init script hands it over only on the web app's origin. A load error while the address is off the web app (that page failing, or the going back) is not the builder failing, so it does not offer the browser. Going back reloads the builder (WebView2 keeps no page cache), so unsaved fields would be lost without the discard prompt; React sends its new-tab links through `openExternal`, so only a plain same-tab link to another site would do it.
- **Storage.** The same pre-page script clears the web app's local storage on the first page of each screen (a reload keeps session storage, so it does not clear again mid-session), the screen clears it again as it closes, and a sign-out deletes the whole WebView2 data folder (`clearDocuNinjaWebStorage`), since no web view is alive then.
- **File inputs** are WebView2's own open dialog. Android's go through the app's picker, now limited to the types the input accepts (`dnAcceptedExtensions`); macOS's web view still has none.
- **Pop-ups** are refused (`WebviewPopupWindowPolicy.deny`); React's new-tab links already come as `openExternal`.

## An email preview is a native web view wherever there is one, and a picture, not a page

`HtmlWebView` (`lib/ui/core/widgets/html_web_view.dart`) shows a finished HTML document in a native web view on iOS, Android, macOS and Windows, so an email's `<style>` blocks, tables and images render as a mail client renders them. `TemplatePreviewPanel` uses it, so both email previews do: Settings → Templates & Reminders, and an invoice, quote, credit or purchase order's Email screen. The web and Linux (and a Windows without WebView2) keep the `HtmlWidget` render of the body.

- **macOS had a web view all along.** The preview used one only on iOS and Android, on the belief that `webview_flutter` had no desktop implementation; it has one for macOS (`webview_flutter_wkwebview`), which the builder already used.
- **No script runs.** `previewHtml` puts a Content-Security-Policy (`script-src 'none'`, and `form-action 'none'`) first in the `<head>` that comes before `<body>`: a custom template is user-written HTML, and the pinned package exposes no switch for WebView2's JavaScript (`ICoreWebView2Settings::put_IsScriptEnabled` exists; the fork does not wrap it). `webview_flutter`'s is off as well. The server strips the wrapper's own `<head>`, and a full HTML email pasted into a template's body brings a `<head>` *inside* the body, where a policy is ignored; so a `<head>` after `<body>` does not count, and the tags then go first in the document (after any doctype), where the parser puts them into the head it makes.
- **A tapped link goes nowhere, and never reaches the server.** `<base target="_blank">` sends every link to a new window, which both web views refuse (WebView2's pop-up policy is deny): a link in a preview is often a real portal link, and opening it would mark the invoice viewed and email the company. `webview_flutter` also refuses every navigation but the document's own load; on WebView2 a main-frame address that leaves the document anyway puts the document back, but only after its request went out, which is why the link must not navigate at all. A `<meta http-equiv="refresh">`, which no policy stops, is dropped, as is a `<head>` inside a comment ignored when the policy is placed.
- **It reads light, on white, in either theme.** The panel asks for a white background, and `previewHtml` sets `color-scheme: light only`, so neither a transparent web view over the dark app surface nor WebKit's own dark page (the email styles declare `light dark`) shows dark text on dark. An email that sets its own dark colours keeps them. macOS's web view takes no background colour (the plugin cannot make a WKWebView non-opaque there and throws, which made every macOS preview an error box until `HtmlWebView` stopped asking, `html_web_view_test`); the colour scheme gives it its white page.
- **It fits the pane's width, and on touch a pinch zooms it and a sideways drag pans it.** The server's email is a fixed 570 px table (`email/template/client.blade.php`, both the light and dark styles) under `width=device-width, initial-scale=1.0`, so on a phone it laid out at 1:1 and the right third was cut off (5.1.32 beta, iPhone, Send Email → Preview), and nothing could move it: `WebViewWidget` was built with no `gestureRecognizers`, and a platform view then gets only the gestures no Flutter recognizer around it claims, while the Email screen's `TabBarView` is a horizontal drag that won every pinch and every sideways pan. Three pieces fix it, all in `HtmlWebView` / `previewHtml`:
  - **Fit by CSS `zoom`, not by viewport.** `previewContentWidth` reads the widest fixed width the markup declares (a `width="570"` or inline `width` / `min-width` in px on a table, cell, div or center; a px width in a `<style>` block), since no script runs to measure the page; a fluid element (`width: 100%`), `max-width` and images do not count, so the "plain" style and a fluid custom template are never scaled. **Nothing inside a comment or an `@media` block counts.** The server's own "View invoice" button (`HtmlEngine::buildViewButton`, in every default body) carries an Outlook-only `<!--[if (gte mso 9)|(IE)]><table style="width: 600px;">`, which read the 570 px wrapper as 600 and scaled a fluid custom template that had the button; and a responsive template (Unlayer, Beefree, Foundation) sets its desktop width (580–680) inside `@media (min-width: …)`, a query a phone does not match, so it was shrunk to 50–60 % though its mobile rules already fit. Comments (`<!-- -->`, and `/* */` in CSS) are stripped first, and `@media` blocks are skipped with their braces matched. `previewFitZoom` turns that and the pane's width (plus 16 px of body margin) into a zoom, floored to a 0.05 step (a resizing window reloads every few dozen pixels, not every frame), and `previewHtml` puts it on `:root`. **It fits fully only where a pinch can zoom back in** (iOS, Android: never below 0.25, `kPreviewTouchZoomFloor`); on macOS, whose WKWebView has no magnification (`allowsMagnification` is off), and Windows (only Ctrl+wheel) it stops at 0.8 (`kPreviewDesktopZoomFloor`), so a narrow pane keeps readable text and the rest of the email scrolls sideways. A wider viewport would only have worked on iOS: `webview_flutter_android` sets `setUseWideViewPort(false)`, so Android ignores the tag, and macOS's WKWebView and WebView2 ignore it too; CSS zoom re-lays out the page (crisp text, not a bitmap) on all four. A document whose width the markup does not declare is not fitted, and on touch is panned.
  - **Our viewport, the only one.** Every `<meta name="viewport">` in the document is dropped (WebKit takes the last one) for `width=device-width, initial-scale=1` with no `maximum-scale` or `user-scalable`, so iOS starts at the fitted size and zooms in from it. Android's built-in zoom is on in the plugin already (`setBuiltInZoomControls(true)`, its buttons hidden).
  - **The web view claims its gestures** (`kHtmlWebViewGestures`, an `EagerGestureRecognizer`). Swiping between the Email screen's tabs no longer works over the preview itself (the tab strip and the rest of the pane still do), which is the price of panning it. No host puts a preview in a vertical scroll view (its frame is always bounded: the Email screen's Preview tab, Templates & Reminders' side pane and its full-screen preview), so nothing loses a drag. WebView2's `Webview` forwards its own pointer events and needs none.
  - **The first load waits for the first layout**, so the preview is not loaded unfitted and then again fitted; a layout that does not change the zoom, and a rebuild, reload nothing. The web and Linux fallback (`HtmlWidget` of the body, no 570 px wrapper) and the PDF tab are unchanged. Pinned by `html_preview_test` (the viewport, the zoom and its two floors, the server wrapper reading 570 with and without the button, a fluid wrapper with the button and an Unlayer-style `@media` width reading none) and `html_web_view_test` (one fitted load on iOS and Android, 0.8 on macOS, a reload on a width that changes the fit, the eager recognizer inside a `TabBarView`).
- **The preview stays up while the next one loads** (`_PreviewStates`), under a thin progress bar: swapping it for a spinner on every debounced edit tore down its web view, and on Windows the WebView2 process, and started another.
- **Too large for WebView2** (`NavigateToString` takes 2 MB; an email with big inline images) shows the fallback rather than a blank page.
