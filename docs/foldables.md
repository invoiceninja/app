# Foldables and the iPhone Duo

Companion to CLAUDE.md § Design system (v2). How the app behaves on a foldable — the iPhone Duo (iOS 27), Galaxy Z Fold, Pixel Fold — when it opens, closes or is held half-open: what the device tells Flutter, the state a resize used to cost and what now keeps it, the book-posture split, where every dialog anchors, and what is still waiting on Flutter.

## A fold resizes the app in place: what moves between breakpoint branches keeps one key, a fold is read only through `fold_geometry.dart`, and every `showDialog` passes `anchorPoint`

Three rules, one cause: opening or closing a foldable is a **resize of the running app**, not a relaunch. iOS 27 keeps the scene connected (Apple's iPhone Duo guidance: fold/unfold is a size-class and trait change); Android keeps `MainActivity` alive because its `configChanges` covers every size, layout and input change (`test/lint/main_activity_config_changes_test.dart`). So every widget on screen lives through a breakpoint flip — and anything the flip rebuilds from scratch loses what the user was doing.

- **Keys.** Wherever a breakpoint swaps the shape of the tree (`Stack` ⇄ `LayoutBuilder`, a `Row` of `Expanded`s ⇄ a `Column`, a page ⇄ a card), the subtree that moves keeps one key, or one shape. The cases fixed: see § What a resize used to cost, below.
- **One reader.** `lib/ui/core/fold_geometry.dart` is the only file that reads `MediaQuery.displayFeatures` (`test/lint/fold_geometry_lint_test.dart`), so the master-detail split, the settings split and Material's own `DisplayFeatureSubScreen` agree on where the fold is.
- **Dialog anchors.** A route on the root navigator opens in the start half of a folded screen unless given an `anchorPoint` — over the list, for a record's delete confirmation. Every `showDialog` / `showGeneralDialog`, `showDatePicker` / `showTimePicker` / `showDateRangePicker` and root-navigator `showModalBottomSheet` (`useRootNavigator: true`) in `lib/ui` passes `anchorPoint: foldAnchorPoint(context)` (ignored by Material when there is no fold), or says why not with `// fold: <reason>` (same lint, which parses each call's own top-level arguments — a first regex missed nested type arguments and let 25 calls through).

## What the device reports

| Device | Closed | Open | The fold |
|---|---|---|---|
| iPhone Duo | phone width (< 600 pt), compact — a phone | 951 × 669 pt (669 × 951 portrait), regular/regular | a 40 pt `division`, reported only while half-open (the simulator numbers in flutter/flutter#193025) |
| Pixel Fold | 412-dp phone | ~841 × 701 dp | zero-width `fold`, `postureHalfOpened` while half-open |
| Galaxy Z Fold | phone | ~707 × 823 dp | zero-width `fold` |

- **Android** maps Jetpack's `FoldingFeature` to `DisplayFeatureType.fold` / `.hinge` and `postureFlat` / `postureHalfOpened` (Flutter's `FlutterView.java`, API 28+). Works today.
- **iOS**: Flutter 3.50's embedder reports **no** display features (`window.dart`: "populated only on Android"). The Duo's hinge (`UIHingeInteraction`, `UIView.reservedRegions(.division)`) reaches `displayFeatures` only with flutter/flutter#193025, still open — see § Waiting on upstream. Until then the Duo gets everything in § What a resize used to cost and nothing in § Book posture splits the master-detail layout and settings at the fold.
- **The iOS SDK decides whether the Duo even resizes.** An app linked against the iOS 26 SDK is letterboxed at an iPhone aspect ratio on the inner display; only the iOS 27.1 SDK (Xcode 27.1) lays out edge to edge, and linking iOS 27 makes the app resizable with no opt-out. So the iOS builds run on Xcode 27.1: CI's `apple-ios` job and `appstore-ios.yml` use GitHub's separate `xcode-27` image (the `macos-26` image has no Xcode 27), pinned with `xcode-select` because that image's default moves. macOS stays on Xcode 26.4.1 (`apple-macos`) so a macOS-SDK change never rides along. A local iOS build needs Xcode 27.1, which needs macOS 26.6+.

### What the open Duo does to the existing breakpoints

| State | Window | `isPhone` | Rail (≥ 600) | Master-detail |
|---|---|---|---|---|
| Closed, portrait | phone width | yes | no (drawer) | full page |
| Closed, landscape | phone, on its side | yes | ≥ 600 wide: yes | full page |
| Open, portrait | 669 × 951 | **no** | yes — content ≈ 437 | full page (< 1024) |
| Open flat, landscape | 951 × 669 | **no** | yes — content ≈ 719 | full page (< 1024) |
| Book posture | 951 × 669, vertical fold | no | auto-collapsed (64) | **split at the fold** |

The breakpoints themselves are unchanged (a decision, not an oversight): open flat, the Duo behaves like an iPad mini. Folding or unfolding crosses **600** (the shell's rail ⇄ drawer, every `isWide`, `FormFieldPair`) and **`isPhone`** (the record layout, the dashboard's column count, the "Hide empty panels" default — all accepted flips, documented here rather than pinned: `hide_empty_panels_controller.dart` stores a null default precisely so a foldable adapts). A Galaxy Z Fold in landscape, or an iPad, can also cross 1024.

## What a resize used to cost

Each was invisible until a window changed size under a user mid-task. Each has a test that fails on the old code, except the list's row carry and the line-item picker's width, which need the full list and picker harnesses.

- **The master-detail list remounted** — scroll, search text, multiselect — when a phone opened a record (slot 0 went from the list to `Offstage(list)`) and whenever the layout crossed `Breakpoints.slideOver` (the root went from `Stack` to `LayoutBuilder`). `_listKey` / `_paneKey` in `master_detail_layout.dart` reparent them instead (`master_detail_layout_resize_state_test.dart`). Two side effects the reviews caught: the kept list kept an open drawer too, invisible behind the record, eating the first Android back — `_closeCoveredListDrawer` closes it when a record covers the list — and it kept keyboard focus: a search field focused beside the record in the split stayed focused once the device went flat, the keyboard up over the record and typing filtering the hidden list (`master_detail_layout_fold_focus_test.dart`). Hiding the list now drops its focus; `ExcludeFocus` alone does not, because a focused field reparented under it keeps its focus.
- **The field being typed in remounted** when its `FormFieldPair` crossed 600 (`Row` of `Expanded` ⇄ `Column`): focus, caret and keyboard gone. One `Flex` with flipped direction and `Flexible(flex: 0 | 1)` slots keeps the same elements (`form_field_pair_resize_test.dart`). The ≥ 1000 two-column edit layouts (`client_edit_layout.dart` and friends) still swap shapes — no foldable's content reaches 1000 (951 − 64 is the widest), so they were left.
- **The list lost its place** crossing 600: the table and the narrow cards are different scroll views, so the new one started at the top. `_carryTopRowAcrossWidthClass` carries the position across as a fraction of the whole scroll extent — no row-height estimate (a card is well over its 52 px floor), so it lands near the same rows.
- **The command palette lost its query** when `isPhone` flipped its page ⇄ card presentation: one `GlobalKey` in `showCommandPalette`.
- **A dialog sized itself once, at open**: the line-item picker measured `dialogWidth` before pushing, leaving a 720-wide dialog in a ~400 window after a fold. Measure in the builder. The dialog-vs-sheet choice is still made at open — a sheet left on a wide window is fine.
- **Anchored popups pointed at nothing**: the theme menu and company picker are placed at a rail button's global position taken at open, and the rail becomes a drawer below 600. `DismissOnWindowResize` closes them on a size change (not on the keyboard, which changes `viewInsets`, not the size). Material's `showMenu` menus clamp themselves to the screen and are left alone.
- **The drawer came back open.** Each screen passes `drawer: globalNav ? null : const AppDrawer()`; unfolding with the drawer out removes it, but the `Scaffold` keeps `_drawerOpened` (and `closeDrawer()` is a no-op with no drawer), so the next fold brought it back open. `StaleDrawerGuard` notes a drawer disposed while its Scaffold says open, and closes the one that comes back. "Mounted while open" would not do: a closed `DrawerController` doesn't build its child, so opening a drawer is exactly what mounts it. The returning drawer animates shut rather than snapping (it is rebuilt at value 1) — cosmetic, accepted.
- **The timer pill covered the field being typed in** on a wide touch window with the keyboard up (an open Duo leaves ~330 pt). It goes offstage while the soft keyboard's inset is over 150 pt — above the 55–70 pt shortcut bar an iPad shows with a hardware keyboard and the ~100 dp IME toolbar some Android keyboards keep beside one — read from the `View`, because the shell `Scaffold`'s body has the inset removed.

## Book posture splits the master-detail layout and settings at the fold

Half-open with a vertical fold, the list goes in the half before the fold, the record in the half after, and nothing is drawn on the fold. "Before" is the start side: the **right** half in a right-to-left locale — the fold is physical, so RTL mirrors what goes where, not where the halves are.

- **What counts**: a vertical fold that splits the window — half-open, or a hinge with width even when flat — the same features Material's dialogs avoid (`DisplayFeatureSubScreen.avoidBounds`).
- **Debounced** (`FoldPostureHost`): entering waits for 300 ms of an unchanged splitting fold, because a phone being opened passes through half-open on its way to flat, and a hand adjusting the angle crosses the threshold more than once. Leaving is immediate — there is no fold left to lay out around. `bookFoldOf(context)` = the debounced flag **and** a live fold in the local `MediaQuery`, so the rect is always current.
- **The rail collapses** while the posture lasts (`SidebarController.setFoldCollapsed`), never written to the preference. Every renderer reads `sidebar.effective` / `effectiveValue` — the content inset, the rail's width, the timer pill, the frameless title bar and `settingsIndexRedirect` — or the inset and the rail disagree. The collapse button still works: in book posture it expands for as long as the posture lasts (and clears a stored "collapsed" — expanding is then what was asked for — which collapsing again in the same posture puts back) — leaving the list half ~224 pt on the Duo, ~188 on a Pixel Fold; the user asked for the rail, so the split keeps no minimum. The host clears the collapse when it is disposed mid-posture (a sign-out), or the next session's rail stayed collapsed against the preference.
- **The shell re-bases the fold into its content's coordinates** (`rebaseDisplayFeatures`, translated by the rail in LTR, not at all in RTL where the content starts at x = 0). Without it the split, which measures from the content's origin, put the list half across the fold (64–519 in the window). `size` stays the window, because `Breakpoints` reads it as the window. Measured with the SDK's own math: a sheet on a nested navigator beside the rail lands on the right side of the fold either way (`DisplayFeatureSubScreen` pads from `MediaQuery.size`); the re-base makes an end-side one start exactly at the fold instead of 64 px past it (`fold_geometry_test.dart`), at the price of a start-side one ending 64 px before the fold on a screen that does not split (the dashboard, say) — accepted.
- **Always split, even with no record open.** The end half then says "No record selected" and offers "New <entity>" where the user may create one — never an auto-selected record (it would fetch, and open, something nobody asked for). Splitting only while a record is open would reflow the list between table and cards on every open and close.
- **The pane in the split** has an X but no back arrow and no full-screen toggle (`F` is inert): detail, edit, new and `?view=full` all render in the end half, because a centred full-width form at ~950 pt sits exactly on the hinge. The edit-opens-full-width redirect is skipped, and the list row stays highlighted (`editorCoversList` is false in book posture). Entering the split with a record open scrolls its row into view.
- **Each half is its own screen to display features and side insets** (`foldHalfMediaQuery`): the fold is removed from its `MediaQuery`, so a sheet opened from the record fills the record's half, and nothing inside splits again. `size` stays the window — `Breakpoints.*(context)` and `isPhone` inside a half still see 951 — so a layout in a half measures itself with a `LayoutBuilder`. Not `MediaQueryData.removeDisplayFeatures`: that measures the half against the window while the box starts past the rail, and would drop the right-hand safe-area inset of a half that does reach the right edge.
- **Settings split at the fold** the same way — each half in its own `MediaQuery` (`FoldHalf`; not while the invoice designer hides the menu, when the section spans the fold), without which the section's Navigator, starting after the fold, still saw it: a menu landed off-screen and a sheet came out zero-wide — whenever the half before it holds the 280 px menu (`settingsSplitsAtFold`) — even below the usual 880 two-pane width (a Pixel Fold's content beside a collapsed rail is ~777). `SettingsShell` measures that half in content coordinates; `settingsIndexRedirect` — and a settings-hosted list choosing its back arrow — measure it from the window (`settingsFoldStartHalf`, which always reads the root navigator's `MediaQuery`: inside a half the fold has been removed, and a list that asked its own got null and pointed "back" at a `/settings` that redirects away). They must agree, or the user is stranded on a section with no menu — `settings_fold_start_half_test.dart` pins the same number from the window, the re-based content and a half, LTR and RTL. With the rail expanded no foldable's half holds the menu.
- **Not split**: tabletop (a horizontal fold) — Material's dialogs and sheets already avoid it; the dashboard grid, the calendar month, the invoice designer and the kanban board (which scrolls anyway).

## Where a dialog opens on a folded screen

`showDialog` wraps its route in `DisplayFeatureSubScreen`, which picks the sub-screen nearest `anchorPoint` — and with none, the start half. `foldAnchorPoint(context)` returns the caller's centre in window coordinates, or null for a context that is gone. It anchors with no fold too, where Material ignores it, because the sub-screen is chosen again whenever the display features change: a dialog opened while flat otherwise jumped to the list's half the moment the device half-opened. Four app-level dialogs (a progress spinner, a boot notice, Contact Us, the first-run Welcome) carry `// fold:` instead. Sheets need nothing: a sheet on a half's nested navigator fills that half. Picker popovers hang off their field and stay in its half; the wide toast (≤ 400 px, top-end) already fits the end half.

## Reviewing it without a foldable

Debug Panel → **Simulate fold** (`Services.simulateFold`, in-memory) lays a 40 pt half-open fold down the middle of the window through `MaterialApp.builder` (`FoldSimulator`) — the only way to see book posture on iOS until Flutter reports the Duo's hinge, and on an iPad, desktop or the web. Android's emulator has foldable images (Pixel Fold, 7.6" Fold-in) with posture controls, but their fold is zero-width, so the 40 pt gap is covered by unit tests. Xcode 27.1's iPhone Duo simulator covers the resize itself (all four poses); it cannot show book posture until #193025 lands.

## Waiting on upstream

- **flutter/flutter#193025** — populate `MediaQuery.displayFeatures` on iOS from `UIHingeInteraction` and `reservedRegions` (iOS 27.1 SDK only). Open, changes requested (Nov 2026). When it reaches a stable Flutter we build with the 27.1 SDK, book posture lights up on the Duo with no app change; verify with the simulator's half-open pose, then flip FEATURES.md's "Foldables: book posture splits…" row to ✅. Its regions lag the hinge, which the 300 ms debounce absorbs.
- **flutter/flutter#195508** — the inner → outer display geometry update; on master, not in 3.50.0. Low impact: the app reads no `PlatformDispatcher.displays`.
