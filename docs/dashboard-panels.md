# Dashboard panels

Companion to CLAUDE.md § Dashboard panels. The main file carries the registry shape — how a panel is declared, ordered and hidden — and the rule for each behaviour; this doc carries the evidence, almost all of it from the task-calendar panel, the first Drift-backed one.

## The task-calendar panel, and the eleven things that hold it up

**The task-calendar panel (invoiceninja/flutter#137) is the first Drift-backed one, and almost everything load-bearing about it is invisible at the call site.** It shows a month as a 7×6 grid tinted and bar-filled by the hours booked on each day, so a user on the phone can see whether they are free before agreeing to a date. Eleven things matter. **It must keep itself alive** (`AutomaticKeepAliveClientMixin`): both dashboard bodies are lazily-collected `ListView`s and the panel is appended *last*, so it starts off-screen, and a plain `StatefulWidget` there is garbage-collected past the cache extent — taking its view model, its Drift subscription, the month the user paged to and the fetch latch with it, so every scroll back would reset the month and re-request. Every other dashboard card is stateless, so nothing else in the feature guards this; `task_calendar_card_test.dart` pins it by scrolling a tall list and checking the month survived, and that case genuinely fails without the mixin. **Nothing under the card may be a `LayoutBuilder`** — `_MultiColumnGrid` wraps every wide-grid row in `IntrinsicHeight`, which throws on an intrinsic query against one in debug and silently answers 0 in release; `Center` is genuinely inert under an intrinsic query; `ConstrainedBox` — which is what the `kMiniCalendarMaxWidth` cap uses — is **safe but not transparent**, since `RenderConstrainedBox` forwards the *incoming* width to its child unclamped, so the body is measured at the full column width and laid out at the cap. Nothing under it may change height with width (the caption is `maxLines: 1` for exactly that reason). That cap is **not** a wide-desktop nicety: the bottom grid stays one column from 600 px to 1199 (it only splits at 1200), so without it a 768 px tablet pane renders seven ~110-165 px columns against a ~38 px row — a month grid stretched into a banner. **The cell tint rides on the cell's own `Material`**, never a `DecoratedBox` under the `InkWell`: ink features paint *before* the child subtree, so an opaque fill below the ancestor Material swallows the splash — the same mechanism that makes `Ink` banned. (The shipped `_DayCell` in `date_range_picker_button.dart` shows both halves: its edge branch uses a local `Material`, its range band a bare `ColoredBox` that eats its own ripple.) **The tint is `Color.alphaBlend(<statusToken>.withAlpha(α), tokens.surface)`, not the `*Soft` token** — `surface` is user-overridable (`CustomToken` is `{background, surface, ink, border}`), so a fixed pale-green would sit on an arbitrary background and strand `ink`; blending into the live surface keeps every cell near it, `_deriveAccentSoft`'s idiom. The hues are `paid` → `sent` → `overdue`, deliberately the **status** tokens: none is in `CustomToken` and every preset keeps the hue family, so no override can invert the scale — unlike `accent`, whose second stock swatch clamps to near-black in light mode. **The bar is not redundant with the tint**: the tint is three buckets while load is continuous, so 5 h and 7 h are both "limited" but visibly different, and the bar's *length* is what keeps the signal alive under red-green colour blindness (colour is never the only cue). **Out-of-month days dim their NUMBER only** — the tint and bar stay at full strength, the reverse of `TaskCalendarDayCell`'s whole-cell `Opacity`, because the panel exists to answer "can you do the 2nd?" and the 2nd lands in the spill row; dimming the one signal it is for would be exactly backwards. **`Semantics(excludeSemantics: true)` must re-declare `onTap`** or the cell becomes a button a screen reader can announce but not activate, and its label speaks **decimal hours with a unit** rather than `formatDuration`'s `H:MM`, which in a *calendar* is heard as a clock time — the same ambiguity that keeps hours out of the cell itself. The `Tooltip` is gated on `!Env.isTouchPrimary`: it is a `StatefulWidget` owning an `OverlayEntry`, and 42 of them on the app's landing screen is a real cost for something touch can only reach by a long-press nobody will try. **It is gated on `can('view_task')`, unlike its six siblings** — they render server-fed data the API has already permission-scoped, so an empty card honestly means "nothing to show", while this one reads the *local* tasks table and a user without the permission has none in Drift, so an ungated grid would paint every day unbooked: a positive claim of availability rather than an absence of data (`RunningTimerPill` gates on the same key for the same reason). **`Today` renders only off the current month**, its slot reserved, since always-on it does nothing on the month the panel opens to. And the panel's one accepted cost is that `watchAllActive` — an unLIMITed `select(tasks)` that JSON-decodes every active task's payload per emission — now runs on the route the app opens onto; it cannot move into SQL because a task's day and durations live only inside `payload`, and the real fix is a `calculated_start_date` column on the Drift table (which would also close the device-vs-company timezone gap and unblock sorting by date), deliberately out of scope on a shipped app.

## Per-day load buckets per time entry, not per task

**Per-day load is one rule in one leaf, and it buckets per time ENTRY.** `lib/domain/tasks/task_day_load.dart` owns `kFullDayLoad` (8 h), `taskLoadByDay`, `dayLoadBucket` and `dayLoadFraction`. `tasksByDay` answers a different question — which day a task *starts* — and drops every later day it was worked on, so a task with entries on Monday and Wednesday would colour only Monday. (The month calendar no longer places its chips with it: `tasksByActiveDay` puts a task on every day one of its entries touches, an overnight entry on both of its days, bounded to the grid — React #3378. The *load* deliberately stays per start day, below.) The per-entry rule is the one `TaskWeeklyViewModel.secondsFor` already applies, and `task_day_load_test.dart` asserts `taskLoadByDay` and `secondsFor` agree day for day, which is what stops the panel and the timesheet disagreeing about the same Tuesday. Consequences: an entry lands **entirely on its start day** (a 20:00→04:00 session, or a timer still running from yesterday, counts wholly on the first day — imperfect for availability, but diverging from the timesheet would be worse); `now` is a required parameter so a running entry is measured against an injectable clock; the result is a snapshot at the caller's last notify, **not a ticker**, because re-laying out 42 cells at 1 Hz to move a 3 px bar is not worth the frames; and `dayLoadBucket` compares whole `Duration`s rather than a ratio, so the 4 h and 8 h boundaries cannot land on a float edge. Fixtures use the local `DateTime(...)` constructor and one `.toLocal()`-derived UTC case — check with `TZ=UTC flutter test`.

## The month window is fetched by the view model, month-aligned

**The month window is fetched from the server, by the view model, and it is month-aligned for a reason.** On a server with `TaskFilters::activity_dates` (`ServerFeatures.taskActivityDates`: hosted always — its version header lags — or self-hosted 5.13.43+) the VM asks for `activity_dates=<from>,<to>` — tasks whose activity *overlaps* the window, however long ago they were opened — over just the grid (`firstOfMonth − 6` … `+41`), and the lookback below is moot. Otherwise `TaskCalendarViewModel.ensureMonthLoaded` pages `repo.ensurePageLoaded` with `extraFilters: {'date_range': {'calculated_start_date,<from>,<to>'}}` — a **one-element** set, since `ensurePageLoadedTemplate` serialises a filter's values with `join(',')` and a second element would corrupt a 3-part value into a 4-part one. It lives on the VM rather than on either screen so the Tasks calendar and the dashboard panel get it *structurally*, with neither call site having to remember. The window is `firstOfMonth − kTaskMonthLookbackDays` to `firstOfMonth + 41`, **never grid-aligned**: `calendarFirstDayOfWeek` resolves the company setting *or the device locale* and both hosts correct the seeded `firstDayOfWeek` on their first frame, so a grid-aligned window would shift under `setFirstDayOfWeek` and fire a second request on every calendar open outside a Sunday-first locale — `task_calendar_month_fetch_test.dart` pins exactly that. **The trailing bound is `+41` from the FIRST of the month, and the arithmetic is the part to get right**: `monthGridDays` is always 42 cells from a start that is never later than the 1st, so `firstOfMonth + 41` covers the grid whatever the week start, with slack equal to the leading-blank count. A margin measured from the month *end* instead has to be **14** (a 28-day February whose 1st falls on the week start spills exactly that far) — the `+6` this shipped with left part of the rendered grid unfetched in **383 of the 588** month × week-start combinations, and those cells then paint "free" off whatever the local cache held, which is the one claim the panel must never make by accident. The 90-day lookback is a mitigation, not a proof: the server's `calculated_start_date` is harvested from `time_log[0]` — the **first** entry, not the earliest — and shifted by the *company's* utc offset, so a task opened in August and still being logged against in September is invisible to a naive September window, and no width fixes that in general. The fetch is bounded at 5 pages and **never throws**: `CompanySwitchedException` and `NetworkException` log at `fine`, everything else at `warning`, every arm releasing the latch. The window maths and the two latch checks sit in `ensureMonthLoaded` and cannot throw (pure `Date` arithmetic); the `try` begins at the page sweep inside `_runWindow`, and its catch is deliberately **bare rather than `on Exception`** — nothing awaits the constructor's future, so an escape becomes an unhandled async error, and the repository doubles in the sibling suites raise `UnimplementedError`, which is an `Error`. **Completed windows and in-flight ones are tracked separately, and collapsing them re-introduces a race.** `_loadedWindows` is what has finished; `_inFlightWindows` maps a window key to the sweep running for it, registered before `ensureMonthLoaded` returns — no other caller can run between the lookup and the claim — so two month taps join one walk. `invalidateLoadedWindow` (the dashboard's pull-to-refresh hook) clears only the first: clearing a live claim would let a refresh landing mid-sweep start a second concurrent walk of the identical window, and the first walk's failure arm would then release the key the second was holding, freeing a third. The loop also **re-checks `_disposed` after every page** — `dispose` cancels the Drift subscription but cannot interrupt a `for`, and on a company switch the next page would otherwise go out under the *new* company's token for the *old* company's window, only to be discarded when it arrived. **A successful sweep notifies; a failed one does not.** Leaning on "the upsert re-emits through the watch" is wrong for the case that matters: `upsertAllPreservingDirty` early-returns on an empty batch, so a `{"data": []}` response writes nothing, drift raises no table update, and the stream stays silent — which is precisely a new account or an empty month, the one state the "nothing booked" caption exists for. The failure arms stay silent because nothing observable changed there, and a best-effort top-up that fails must remain invisible. Three costs are accepted rather than fixed: a cold start now adds up to five task requests to the boot fan-out on the default post-login route; the latch is per-instance, so the dashboard card and the Tasks calendar screen each fetch the same window while both are mounted (a shared cache would need a logout fan-out to be leak-safe), and holding the month arrow queues one bounded sweep per month with no supersession. One more silent degradation worth knowing: the server falls back to `date` for a column it does not recognise, and `tasks` has no `date` column either, so an old self-hosted install without `calculated_start_date` gets **no filter at all** rather than an error — harmless, since that is what `refreshAll` fetches anyway, but undetectable client-side.

## `hasLoaded` is not enough to claim availability

**`hasLoaded` is not enough to claim availability, and the gate for that claim is not `Opacity`.** A Drift watch emits on subscribe, so `hasLoaded` flips within a frame of construction — before the window fetch that fills the grid's far edges resolves. The confident sentence ("Nothing booked this month") therefore waits on `hasLoaded && !isLoadingWindow`, while the dimming waits only on `hasLoaded` (dimming for every month change's round trip would flicker). And the dimming itself is paint-only: without the `ExcludeSemantics` + `IgnorePointer` beside it, an un-loaded grid still announces "<date>, Free" for all 42 cells to a screen reader and still accepts taps into a day it has no data for — the positive claim of availability the `view_task` gate exists to prevent, made out loud. The caption's predicate is also over the **visible grid** and on the **duration, not the key**: `taskLoadByDay` inserts a key for a zero-length entry too, so a month whose only rows are `start == end` would otherwise suppress the caption over a blank grid.

## The today marker takes `onAccent`, never `accentInk`

**The "today" marker takes `onAccent`, never `accentInk`.** `accentInk` is the *text-on-surface* accent, derived by shifting `accent`'s lightness precisely because `accent` fails as ink — pairing the two gives about **2:1** in either brightness, and every other call site correctly pairs `accentInk` with `accentSoft`. `onAccent` (`design_tokens.dart`, modelled on `onOverdue`) computes the accent's relative luminance and returns whichever of white / near-black wins, so it follows a user-overridden accent: 4.34:1 on the stock blue — its ceiling, no foreground clears 4.5 against that hue — and 5.5:1 on the green swatch, where white would be 3.3. The full-size `task_calendar_day_cell.dart` had the same 2:1 pairing and is fixed with it.

## The cards, the legend, the grouping and the panels sync under flutter_dashboard in company_user.settings

**What syncs, and where.** Three clients read one account, and each keeps its dashboard somewhere else:

| Client | Where | Format |
|---|---|---|
| Old Flutter app (admin-portal) | `company_user.settings.dashboard_fields` | `[{field: 'total_active_invoices', period: 'current_period', calculate, format}]` |
| React | `company_user.react_settings.dashboard_fields` | `'field\|period\|calculate\|format\|index'` strings |
| This app | `company_user.settings.flutter_dashboard` | below |

This app keeps everything under its own key in the object the old Flutter app uses, and **reads and writes nothing in `react_settings`** — that blob is the React team's (`docs/user-settings-storage.md`). The old app's `settings.dashboard_fields` uses other field names (`total_` prefix, `current_period`, `average`) and fields the server's `calculated_fields` doesn't take, so it is neither read nor written either. `flutter_dashboard` holds:

- `cards` — `DashboardCardConfig.key` strings (`field|period|calculate|format`), the form `nav_state` stores.
- `grouping` — `day` / `week` / `month`, the `ChartGrouping` names.
- `panels` — `['<kind>|<1|0>', …]`.
- `chart_series` — the legend's visible series, as `ChartSeriesId` names (`invoices`, `payments`, `expenses`). A legend stored before the bar chart may also name `outstanding`; every reader matches names against the enum, so it is dropped, and a list naming only it falls back to the default (`dashboard_view_model_test` "a stored outstanding series is dropped").

The dashboard is therefore no longer shared with the web client: a card added in React does not appear here, and the reverse. Before November 2026 the cards and the grouping were written into React's own `dashboard_fields` and `preferences.dashboard_charts.default_view`; that was withdrawn so this app can never disturb what React stores.

**A change sends only its own path.** `_Synced` names the four (`flutter_dashboard.cards`, `.grouping`, `.panels`, `.chart_series`), and a write carries only those changed since the last one (`_syncDirty`). Sending all four on every tweak — the first version did — laid this device's copy of the other three over the server's, so a legend toggle on a device that had not refreshed reverted a card edit made on another.

The date range, the Invoices and Quotes panels' tabs and "Hide empty panels" stay on the device: a range is a view of the moment, and the last is a phone's scroll budget (below).

**The server replaces the object, so the outbox carries a change.** How a change is queued, laid over the freshest copy when sent and laid over a `/refresh` capture is `docs/user-settings-storage.md` — the dashboard only calls `UserSettingsRepository.patchSettings`. That is a no-op until a login has stored the settings row; until then the dashboard is device-local, as `nav_state` alone made it.

**Adopting is not writing.** `DashboardViewModel._adoptSynced` takes the settings over `nav_state` on open and live from the watch (another device's change arrives with the next `/refresh`; added cards are fetched, dropped ones purged as `removeCard` does). Adopting writes `nav_state` only. Only a change to a synced preference (`_schedulePersist(sync: …)`) — or a key the settings lack while this device has a non-default choice, so the first device to sync seeds the rest — writes a change. That seeding is also the migration: a device that ran a build which synced through `react_settings` holds its choices in `nav_state`, finds `flutter_dashboard` missing, and writes them up. And it is the recovery when the old Flutter app saves its settings and, sending only the fields it models, erases `flutter_dashboard`. A change waiting on the debounce sets `_syncPending`, which ignores emissions until its write lands: a capture meanwhile still holds the old value. Tests: `test/ui/features/dashboard/dashboard_synced_prefs_test.dart`, `test/data/repositories/user_settings_patch_test.dart`.

## A new panel goes at its canonical rank

**`DashboardViewModel._parsePanels` (the `nav_state` read and the synced one alike) places a missing kind at its rank in `panelKinds`, not at the end.** The rule it replaced — "append, never splice" — was self-fulfilling: the hydrator appended, so front-loading a constant would have shown a panel first on a fresh install and last on every existing one, and the advice was therefore to declare it last. What made that costly is that `setFilter` calls `_schedulePersist()`, so **anyone who has ever changed the dashboard date range has a persisted `panels` array** — i.e. nearly everyone — and a new panel's declared slot was unreachable for all of them. The Invoices & Quotes panel is a strip of counts meant to be *glanced at*, and on a phone the trailing block already starts ~1150 px down, past the hero, the quick actions (since removed, #164), the past-due card, the chart and the activity feed; appended, it would have shipped where the issue's reporter says a feature "may as well not exist". The rule has to be stated precisely, because two plausible readings are wrong. **Walk `panelKinds` in ascending canonical order; insert each missing kind immediately after the last already-placed kind of smaller rank, or at position 0 if there is none.** Anchoring on the *predecessor* rather than "before the first kind of greater rank" is what keeps a new kind below `past_due` in a save where the user dragged `past_due` down — `dashboard_view_model_test`'s hydrate fixture is exactly that arrangement, and the other reading hoists the panel to the very top. Never `loaded.insert(canonicalIndex, …)`: on a reordered save it shoves unrelated panels around, and it `RangeError`s whenever the saved list is shorter than the index — which `_hydrate`'s `catch` would swallow into a log line while silently discarding the user's whole arrangement. Ascending order matters too, or several missing kinds land in arbitrary relative positions. One property worth asserting because it is easy to lose: a save that *was* the old default now hydrates to the *new* default, so `panelsAreDefault` stays true and the manage dialog's Reset stays enabled — under the append rule it went false for every existing user the day a panel shipped. `reorderPanels`, `reorderTrailingPanels`, `togglePanelVisibility` and `resetPanels` all re-derive from `panelPrefs` or `panelKinds` on every call, so an extra kind at index 1 is transparent to their index maths.

**A new panel also needs its arm in `panelTitleKey`**, which maps a kind to its l10n key. Its `_ => kind` fallthrough makes an arm whose kind and key coincide a no-op — write it anyway, so the switch reads as the complete map it is.

## The Invoices & Quotes panel, and why its per-entity ids are explicit

**It is two panels now — Invoices and Quotes, half width each, side by side — and each row is the shared `DashboardRecordRow`.** The one consolidated card spanned the whole grid as a six-column table (`Type | Number | Client | Status | Date | Amount`, the last `DashboardEntityTable`), and at full width a short row put all its slack after the client's name — the report was "a lot of empty space between the client name and status". A UX review weighed three fixes: the old app's two-line tile (moves the gap, doubles the row height against Compact), capping the client column (shrinks the gap, still fails on a wide monitor) and the split, which it recommended. What the split cost: the mixed `All` / `Draft` counts (57 documents is not a number anyone acts on) and the Type column. What it gave back: Overdue on the Invoices strip — left out of the merged strip only because "Needs your attention" covers it, which made that strip disagree with the invoice list's — a single View All per card, and rows in the same grammar as every neighbour. Details:

- **Two kinds, not one card drawn as two halves** (`DashboardKind.invoicesPipeline` / `quotesPipeline`, gated each on its own module and view permission in `enabledPanelKinds`), so a company with quotes off gets one half panel instead of an empty half. They are adjacent in `panelKinds`, so by default they pair as one row, and neither ever spans (`kNeverSpanPanels`): stretched, a status strip sits in one corner.
- **A saved arrangement naming `invoices_and_quotes` becomes both kinds in its place with its visibility** (`_splitLegacyPipeline`). Left to the canonical-rank placement, a user who had hidden the one panel would have seen two new cards appear. The old `billingTab` seeds both cards' tabs (`invoicesTab` / `quotesTab`), and each heals an id its entity doesn't offer back to `All`.
- **The status pill shows on `All` only** (`DashboardRecordRow.badge`) — on a status tab every row has that status — and it comes **after** the date, in a fixed 84 px column of its own before the amount (a longer word scales down). A pill is as wide as its word, so sized by it a "Past Due" pill took width from the client and the date and neither started at one x down the card. On a phone the pill sits under the amount instead, because there the amount's width varies by row and a pill ending where it begins was ragged too.
- **The date is the document's date; the line under it says how near its deadline is, and only when it is near or gone** (`invoiceRowWhen` / `quoteRowWhen` in `when_text.dart`, fed `BillingPipelineRow.openDeadline`): "12 days late" in the overdue tone, "due in 3 days" within 30 days (`kRowWhenWindowDays`), "expires in 3 days" / "Expired" for a quote, and nothing past the window or on a closed document — a draft, a paid / cancelled / reversed invoice, or a quote no longer out with the client. An invoice counts towards its deposit's due date while one is asked for, the date `Invoice.isPastDueOn` measures. Today is the device's (`Date.today()`).
- **A foreign-currency amount carries "≈ {company-currency amount}" under it on the wide layout** (`approxInBaseCurrency`, `converted_hint.dart`): the amount divided by the document's **stored** `exchange_rate`, the rate the server's own All-currencies totals divide by (`SUM(balance / exchange_rate)`), so the row agrees with the figures above it. Nothing when the document is in the company currency (or the client's currency has not resolved yet), when the rate is zero, or when it is exactly 1 between two currencies — the server's default for a rate never set, which would print the foreign figure under the base symbol. The phone and the Compact density drop it. The client is a `ClientNameLabel` (`DashboardRecordRow.clientLabel`), since these rows carry only the id.
- **Rejected, Cancelled and Expired are on the Quotes strip only while they hold something** (`kOccasionalBillingTabs`, watched on the same count streams the badges use) — three zero tabs wrapped the strip onto a second line to say nothing. The selected tab always stays, so a restored `expired` never vanishes from under the user. The quote list's own strip keeps all three: there they are the way to find one.
- **The view model watches `kDensePanelRows` and the card slices** (3 on a phone, 5 or 8 under Compact), so a density change needs no new view model.

The rest of this section is the merge machinery, which stays: each card passes one entity, and the per-entity ids are what keep it from failing open.

**The consolidated panel (invoiceninja/flutter#155) is a *view* over the invoice and quote badge catalogs, and the one thing that cannot be inferred is which mode id each entity contributes to a tab.** `lib/domain/dashboard/billing_status_tabs.dart` owns the union: a `BillingStatusTab` carries the borrowed `SidebarBadgeMode` for its label and tone plus a **separate, nullable `invoiceModeId` and `quoteModeId`**, and null means "this entity does not participate". That verbosity is the whole design, because **both DAO seams fail *open*, not closed.** `badgeModeListFilter` returns null for a mode a DAO does not recognise and `watchPage` then skips its WHERE; `watchBadgeCount` does `if (extra != null) q.where(extra)` and otherwise counts **every active row** — not zero. So handing the quote-only `approved` to the invoice side would list and count every invoice in the company, and it type-checks, renders, highlights and looks entirely plausible. Of the seven tabs only `All` and `Draft` are mixed; invoices have no `sent`/`approved`/`rejected`/`expired` mode and quotes have no `unpaid`. The **order is derived, not invented**: filtered to each entity, `kBillingPipelineTabOrder` reproduces that entity's own `kListStatusTabs` order — invoices read `draft, unpaid, overdue, paid` (the whole Invoices strip since the split; `paid` joined it in Nov 2026) and quotes read `draft, sent, approved, rejected, expired` — so the panel can never disagree with the list its footer link lands on, and `billing_status_tabs_test` pins that in both directions plus the reverse union, which is what catches a mode added to a list catalog later that never reaches the panel. `unpaid` sits second rather than last because it is not a lifecycle *stage* (draft → sent are stages, approved/rejected/expired are terminal outcomes of a sent quote), so lifecycle order is silent about a cross-cutting money state and parking it last would cost the strip's most actionable number the most travel. A mixed tab borrows the **invoice** side's mode for its label and tone while its badge sums both populations, which is benign only because `draft` is spelled identically in both catalogs — asserted, not assumed. Three more things are load-bearing and invisible at the call site: the card needs `AutomaticKeepAliveClientMixin` (both bodies are lazily-collected `ListView`s, and it is now the *first* trailing panel on mobile, closer to the cache extent than the task calendar ever was); `narrow` is a parameter rather than a `LayoutBuilder`, because the wide grid wraps each row in `IntrinsicHeight`; and it is gated on `view_invoice` / `view_quote`, unlike its six server-fed siblings, for the same reason the task calendar is gated on `view_task` — it reads the local tables, so an ungated strip would paint seven confident zeroes as a positive claim.

## A strip of counts is payload, so it wraps

**`EntityListStatusTabs` has two layouts, and which one is right depends on whether its items carry state.** Above an entity list the strip is chrome over rows that render either way, so a tab scrolled off the edge costs a swipe: it scrolls, with the gated edge fades. Inside this panel the strip *is* the feature — its items carry the counts the whole issue asks for — so an item pushed off the edge hides **state**, which is the same argument `docs/pane-width-and-overflow.md` records for the Tasks filter chips ("a chip pushed off the edge hides an active filter") rather than the one it records for a tab strip. Seven tabs measure ~615 px against a ~334 px phone card *and* a ~570 px card in the desktop two-column band, so scrolled, four counts — including the red `Expired` — sit behind a gradient on a card the user already scrolled ~1150 px to reach. `wrap: true` shows all seven for ~44 px of card height (a third run in German or at a large text scale). It needs no breakpoint: a `Wrap` self-measures, and it is safe under the wide grid's `IntrinsicHeight` because `RenderWrap` answers intrinsics via `getDryLayout` — it is not a `LayoutBuilder`. **Selection has to change with the layout.** The 2 px bottom border takes its meaning from sitting on the strip's own rule; on the first run of a wrapped strip it floats mid-surface and reads as a stray line, so wrapped tabs use an `accentSoft` fill at `InRadii.r2` — the treatment `SidebarNavItem` already uses for this same vocabulary (a label plus a `SidebarBadge`, no rule beneath), and the one `SidebarBadge.active` exists to retune its palette against. The failure direction is then the right one for a density complaint: the strip degrades by **growing**, never by hiding. Two things landed with it that apply to every host: `_StatusTabButton` now declares `SemanticsRole.tab` + `selected` under a `MergeSemantics`, so a screen reader says "Draft, 12, selected" instead of reading seven pairs of unrelated nodes — the role is gated on `onTap != null` because it *asserts* a tap action and the strip stays laid out but untappable during multi-select.

## A tabbed card is the one place the generic empty string is right

**Every other dashboard card names what it has none of — `no_invoices_due_soon`, `no_payments_yet` — and the Invoices & Quotes panel deliberately does not.** The house rule exists because a single-purpose card's title is the only context an empty body has, so "No records found" there leaves the reader to work out what was being counted. A tabbed panel has the answer on screen: the selected tab is highlighted directly above the empty area, so the generic string reads in context, and six per-tab strings would restate a label the user is already looking at. (`_app_pending.json` can only *add* keys, never override one, so a per-tab set is also unusually hard to walk back.) The exception stops exactly there: **`Rejected` keeps its own two-line hedge**, because that tab is local-only until BACKEND.md § F1 ships and an empty body there genuinely does not mean the company has none — which is the case the honesty rule was written for. `BillingStatusTab.isLocalOnly` selects it, and it is a property of the **tab** rather than something the widget derives: asking `statusTabServerFilters` directly answers null for `All` too — whose `kBadgeModeTotal` simply has no `ListStatusTabSpec` — so a derivation at the call site labelled an ordinary unnarrowed server page "not synced yet" on any single-module company, which is the bug this shape closes.

## Most recent needs a tie-break, and epoch 0 leads

**`date` is date-only, so "the five most recent" is decided by the tie-break, and both obvious tie-breaks are wrong.** Every document a company issued today ties on `date`, and `watchPage`'s backstop is `OrderingTerm(expression: e.id)` — a hashid, **ascending, regardless of `sortAscending`** — so the panel's top five would have been an arbitrary, effectively-oldest five. `tieBreakField` (+ `tieBreakAscending`) is the fix, and four properties are load-bearing. It **appends** rather than replacing: rows can tie on both keys (a bulk import shares a date and a whole-second `created_at`), and without the final `id` the order is non-deterministic, so `distinctRows()` can flap between emissions and the cross-entity merge stops being reproducible. It carries **its own direction**, since the `id` backstop's is fixed. It is validated **eagerly** — drift invokes the `orderBy` generators inside `orderBy()`, so an unmapped field throws `ArgumentError` at the `watchPage` call site rather than inside a stream nobody has listened to yet. And **`created_at == 0` must sort FIRST, not last**: the column is `withDefault(0)` and `<Entity>EditViewModel` stamps epoch 0 on a local create, so a plain `created_at DESC` puts the invoice the user just made offline at the *bottom*, where a five-row window drops it entirely. The expression maps 0 to the max signed 64-bit value; `NULLIF(created_at, 0)` is the idiomatic-looking version and is **wrong**, because SQLite ranks NULL below every value and under DESC those rows sort last — the same bug by a prettier route. The Dart-side merge (`compareRows`) restates the identical total order, since merging two individually-correct top-Ns and truncating is only the overall top-N when both halves agree; `billing_recent_order_test` pins the SQL half and `billing_pipeline_merge_test` the Dart half, and each has a case that fails without the epoch-0 rule. One consequence of the panel being Drift-backed: its per-tab top-up passes `ignoreCursor: true` on **every** call, including the unnarrowed ones, because an unnarrowed fetch is not a "narrowed fetch" and `shouldReadCursor` would otherwise send the `updated_at >=` watermark and return a delta rather than a true first page — which would leave the local-only `Rejected` tab with no mechanism at all to pull rejected quotes into the cache.

## An empty panel is dropped from the list, not hidden by the card

**"Hide empty panels" (invoiceninja/flutter#161) is a per-device preference, a panel is empty only once its section has loaded with no rows, and the panel list — never the card — is what leaves it out.** The issue: on a phone, "No upcoming quotes" costs a scroll to say nothing, and a notification centre lists only the apps with something new. **The preference** is `DevicePrefKeys.hideEmptyPanels`, **absent by default**, and absent means *automatic*: `hidesEmptyPanelsByDefault(context)` (`dashboard/helpers/hide_empty_panels.dart`), which is `Breakpoints.isPhone` — touch-primary *and* a short side under 600. `Env.isTouchPrimary` alone is the wrong question, because a tablet is touch-primary too and the issue asks for the default on phones only ("wouldn't make sense on desktops, laptops or tablets"). It is nullable for the `phone_actions_json` reason (a SQL default can't give a phone and a desktop different answers), and it is per device rather than a key in the per-company `dashboard` blob because the trigger is a phone's scroll budget, not a company's data: in the blob it would need flipping once per company, and Device Settings could not reach it. The controller imports no UI; every widget goes through the `effectiveIn` / `setIn` extension beside that helper, so the Customize footer switch and the Device Settings card resolve *automatic* exactly as the dashboard does — a caller that passed its own notion of "phone" (the sheet's `mobileLayout`) would disagree with it in a 600–832 px desktop window, and `dashboard_panel_wiring_test` forbids calling `effectiveFor` / `set` from those two. **Automatic stays reachable**: a switch can only say on or off, so `set` stores null whenever the chosen value is the one the device would pick anyway, and only a *different* answer sticks. Without that, the first flip froze the answer for good — a foldable (a phone folded, a tablet open) or a split-screen window stopped adapting, with no way back short of clearing app data. It is an account preference, so a deliberate sign-out forgets it — and only that: the idle re-lock / 401 path keeps local data, and resetting there would turn a phone user's explicit "off" back into automatic — on — until the next launch. The main-menu and Tasks-layout controllers used to reset on that path (`onBeforeLogout`) and had exactly that bug, worse for the menu: the same user saw the default order after a re-lock, and their next menu edit saved it over their real one. Every preference controller now follows `DevicePrefsStore`, which only a data wipe changes under it, and `test/app/device_prefs_wipe_test.dart` proves each one across both kinds of session end (`docs/device-preferences.md`).

**What counts as empty is the exact state in which a card would say "No …" — `ListSectionState.empty` (`view_models/async_section.dart`).** That enum is the one order every dashboard list surface renders in (`DashboardListCard`, `ActivityCard`, the mobile list cards) and the one `DashboardViewModel.emptyPanels` hides by, through the shared `isLoadedEmpty`: three hand-written copies of it had already drifted once. A `null` section has never been fetched (or its cache row can't be decoded — `_list` turns every successful payload into at least `[]`), so it is `loading` and the card shows a skeleton, not a claim; an error over `null` is `failed` and shows a retry, and a failure is something to share, so neither is hidden. An error over a cached `[]` stays `empty`, matching the wide card, which renders its empty state there too. Only the cache-backed panels can qualify — the view model derives the eligible set as `panelKinds ∩ listKinds` and updates it in `_subscribe`'s `onData`, the only place a section's data changes (`_setSectionError` keeps it). **Invoices & Quotes and the task calendar are exempt, and the reason is mechanical, not taste:** each runs the fetch that fills it from its own view model, so unmounting one while the local cache reads empty would cancel the only request that could prove otherwise and leave it hidden for good; and their "empty" is a *selection* behind tabs or month arrows that lead to data. Past-due's "All caught up" does count as empty — that is the notification-centre reading the issue asks for.

**Why the list and not the card.** § A card that hides itself still costs a gap (`docs/comments-and-activity.md`) applies twice over. Both bodies put a gap per entry, so a card that returns `SizedBox.shrink()` leaves a doubled one; and in the wide two-column grid an `Expanded` keeps its share of the row whatever its child paints, so a self-hiding card leaves half an empty row. The mobile past-due slot and `_trailingPanels` add card and gap together, so dropping the entry drops both, and the wide grid re-pairs its rows. **The rebuild trap is the other half:** a section emission bumps only that section's `_SectionNotifier` (pinned by the first test in `dashboard_view_model_test`), while both panel lists are built under the view model's *global* notify — a filter evaluated there alone would keep whatever the first frame saw. So `emptyPanels` is a separate notifier that publishes only when membership changes, and `HiddenEmptyPanelsBuilder` is the one place the wide grid, the mobile body and the Customize sheet get their `hidden` set from (`dashboard_panel_wiring_test` requires it in all three). It is a `StatefulWidget` for two reasons. It **subscribes only when its view model or preference is replaced**: a fresh `Listenable.merge` per build re-subscribed on every parent rebuild, and the Customize sheet outlives the view model it was opened with — after a company switch disposed that view model, the sheet's next rebuild (a drag, a rotation, a locale change between companies) called `addListener` on the disposed notifier and tripped `ChangeNotifier`'s debug assert. And it **rebuilds only when its answer changes**: with the preference off — the default everywhere but a phone — a panel emptying out changes nothing on screen, so it must not rebuild every card, the chart and the task calendar's day loads beneath it. It wraps **always**, even with the preference off: swapping it for a bare child changes the widget type above the list, which re-creates the `ListView` or grid — scroll position and the Drift-backed panels' state with it.

**The wide grid keys each panel with a `GlobalKey`, because the `ValueKey` it carried never matched anything.** The grid builds unkeyed `IntrinsicHeight(Row([Expanded, …]))` rows, and a key only takes part in matching among its siblings — under `Expanded` it has none. So any change of row *or* column re-created the card: a manual hide or reorder already did it, disposing the two Drift-backed panels' view models, re-running their fetches and sending the calendar back to this month, and a neighbour emptying out would now do it on every refresh that changes emptiness. `DashboardPanelGrid` (extracted so the rule is pumpable — the screen's body never builds in a widget test) owns one `GlobalKey` per kind, per `State` and never static: the framework retakes a keyed element within the frame, since every row rebuilds together, and `AutomaticKeepAlive` explicitly handles a client that moved beneath it. `dashboard_panel_grid_test` fails with `ValueKey` in both the one- and two-column layouts. A State that travels also carries its flags: `DashboardBillingPipelineCard` now clears its tap latch (`_userPicked`) when the company changes, or the new company's late-restored tab was skipped. **Mobile needs no keys beyond the panels'** — `SliverChildListDelegate` matches keyed children by key — but it matches *unkeyed* children by index, so the pinned past-due slot is **one child that is always there** (card and gap, or `SizedBox.shrink()`): a slot that came and went shifted the chart and the activity card, and each shift rebuilt their whole subtrees and dropped any transient state, such as an open chart tooltip. (A fresh fl_chart chart does not animate on mount — it is an `ImplicitlyAnimatedWidget` — so the cost was the rebuild, not a replayed animation.)

**The mobile list cards had to become honest before any of this could default on.** The phone's hand-rolled list card (`_mobileListCard`, since replaced — both layouts now share one set of cards, § One row grammar for every list) rendered its empty message for all three non-row states, so a phone would have flashed "No upcoming quotes" before hiding the panel, and a failed fetch read as "there are none". Its placeholders were made deliberately **compact**, and the shared cards keep that: a failure is an inline message and a `Retry` button, not `ErrorView` — that centres a 56 px icon and a padded button in a scroll view needing ~240 px, and in a fixed box it clipped Retry out of sight and swallowed pull-to-refresh. An empty card is one line. (Loading is a three-row skeleton, sized for the rows that usually follow; the cache means it shows only on a device's very first fetch.) **A phone says what it hid**: the list ends with "N empty panels hidden" (`DashboardCardFooterLink`, with the touch floor) whenever a switched-on, available panel is hidden, opening Customize on the Panels tab — the default is on for phones, so an upgraded user's empty panels simply vanish, and the phone's Customize button opens on the Cards tab. There, a row that is switched on but hidden is captioned "Hidden while empty"; the footer switch shares a single `Wrap` run with Reset, because the ≤ 640 px dialog leaves the panel list only about 30 px below its last row's top and `manage_dashboard_cards_sheet_test` counts on-screen drag handles; its label is `Flexible`, since `Wrap` bounds the row but a plain `Text` in a `Row` ignores that bound and overflowed at large text sizes; and Reset still covers only this company's order and visibility. The Density control (`docs/list-density.md` § Where the setting lives) closes the panel *list* instead, for the same height reason — as the list's footer it scrolls rather than taking a fixed run, and the sheet test scrolls to it. On the wide grid, "Show panels" appears only when a renderable panel was switched off by the user *and* isn't itself empty — otherwise the link would promise panels that stay invisible once switched on. **Testing any of this "on a phone"** needs the reported window to be phone-sized: `setSurfaceSize` sizes the render surface but leaves `MediaQuery` at the test view's 800x600, so either set `tester.view.physicalSize` / `devicePixelRatio`, or override `MediaQuery` in `MaterialApp.builder` — which also reaches dialogs and sheets on the root navigator. (`WidgetsApp` never adds a `MediaQuery` of its own; the `View` does.)

## A panel hides from its own ⋮, and Customize brings it back

**Every panel, and the needs-attention band, has a `⋮` with Hide and Customize; Hide writes the same flag as the Customize switch (`DashboardViewModel.setPanelVisible`), so it syncs like any panel change, and its toast offers Undo and says where to turn it back on.** Before this the only way to drop a panel was Customize → Panels, and the band's row there was titled "Needs your attention" — words the band never prints (it shows only its lists' names: Past Due, Due Soon, Quotes Expiring), so nothing tied what you saw to the switch that hides it. That row now carries those three names as its caption.

- **The menu rides an `InheritedWidget`, not a constructor parameter.** A host wraps each panel it places in `DashboardPanelMenuScope` (`withDashboardPanelMenu`, `widgets/dashboard_panel_menu_host.dart`) — the wide grid's builders, the phone's `_trailingPanels`, and `DashboardAttentionSlot` — and `DashboardCardShell` puts `DashboardPanelMenuButton` at the end of its header when it finds one. The scope carries callbacks, not the view model, so the shell (which frames record and edit screens app-wide) never imports the dashboard. Outside a scope the shell draws no menu (`dashboard_panel_menu_test`).
- **The band places its own button**, because it has no header: at the end of the last list's header side by side, of the tab strip when tabbed, and of the quiet "Nothing past due" line. It draws none while loading or failed, and none when the slot is held open only by the failed-saves alert (`showMenu: show`) — the band is already hidden then.
- **Hide and Undo are idempotent setters, not toggles**, so a double tap or an Undo after the user already switched the panel back in Customize cannot flip it the wrong way.
- **Pointer size is 24 px** so a header does not grow for it; touch is the 44 px floor, pinned the `EntityActionsPopupButton` way (`fixedSize` + `shrinkWrap`, no `visualDensity`).

## The `+` is a FAB that opens a create sheet

**The narrow dashboard's `+` is a bottom-right FAB that opens a sheet of everything the user may create, and `quickCreateEntities` is the one gate for that sheet and for the wide bar's create buttons** (invoiceninja/flutter#164; the wide half is § The wide bar's creates are measured, and one always survives). The report came from a phone tester. Users expected "the most important stuff" under the `+`, as in WordPress's admin bar. The `+` sat in the app bar's top-right corner, out of a thumb's reach, and could only start an invoice. The body also carried a row of New Client / Enter Expense / Reports tiles, which scrolled away with the page.

**What shipped.** `DashboardCreateFab` (`lib/ui/features/dashboard/widgets/dashboard_create_fab.dart`) is a plain `FloatingActionButton` in the screen's own `Scaffold`, at the default `endFloat`, with the tooltip `create_new`. It is narrow-only, like every list screen's `+`, and it is left off entirely when the user may create nothing. Tapping it opens `showQuickCreateSheet`: a "Create New" heading over `QuickCreateGrid`, with one tile per entity, labelled with the same `new_*` keys the list FABs and the create shortcuts use. So three of the tiles read "Enter …". The app bar lost its `+`, and the body lost the whole tile row.

**The entries.** `kQuickCreateEntities` (`lib/domain/quick_create.dart`, a leaf) lists them most-used first. The first four are the reporter's own list (invoice, quote, payment, task), and the next two are expense and client, the creates the tiles used to carry. With three columns on a phone, those six fill the first two rows. `quick_create_test` pins the exact order. It also pins that the set equals `kCreateShortcutEntities`, so an entity that gains a create screen cannot ship in one list and not the other.

**The gate.** An entity is offered only when all three of these hold, and each one is a trap if skipped:

- **It has a registry `newRoute`.**
- **Its module is on.** Payments have no module bit of their own; `moduleForEntityType` puts them on the invoices bit.
- **`can(createPermissionFor(type))`.** Edit rights never imply create, and the permission grid calls transactions `bank_transaction`. There is no `create_transaction` token, so asking for one would hide Transactions from every non-admin, even one who was granted it.

The wide bar's New Invoice button used to check the module alone. A user without `create_invoice` was offered it and then refused on save. The wide bar now draws its buttons from the same list.

**Why a sheet, not a `MenuAnchor`.** The app's touch choosers are already sheets (`showPhoneCandidatePicker`, and the narrow theme and company pickers), and a sheet keeps all fourteen entries within reach of the thumb. A menu anchored to the corner has two problems:

- It would put its first entries at the top of the screen.
- It would not line up with the button. `_MenuLayout` gives a root anchor `parentOrientation: Axis.horizontal`. So when the menu overflows to the right, it takes the `x = allowedRect.right - childSize.width` branch: flush with the safe area, 16 px past the FAB's edge.

**Why the root navigator.** The shell paints `RunningTimerPill` above the branch navigators (its narrow `Stack` puts it after `navigationShell`). A sheet on a branch navigator therefore has the pill floating over its bottom rows, which `task_filters_mixin.dart` already documents for the task filter sheet. `dashboard_create_fab_test` pins the root navigator by asserting that the sheet has exactly one `Navigator` ancestor while the button sits inside a nested one.

**Where a pick goes.** `_DashboardScreenState._create` handles every pick:

- It runs `unsavedChangesGuard.confirmIfDirty` first, as the sidebar's `+` and the create shortcuts do. Every destination is in another branch, and branch state survives a switch.
- It then calls `goToCreateRoute`, not a bare `go`. `stageCreateDraft(basePath, null)` bumps the `/new` route's seed generation, which re-keys a create screen the branch left mounted. Otherwise go_router reuses that screen, still seeded with, say, the client an earlier New Invoice started from.
- The sheet resolves to the picked entity, and navigation starts only after it has been popped, so no modal route is in the way.

**The rebuild.** `_onSessionChanged` used to return early unless the company changed. The session is also rebuilt, for the same company, when its modules, permissions or name change: `AuthRepository` re-derives `companies` from the companies table. So a permission granted mid-session left the `+` stale until the next company switch. The same-company branch now calls `setState` ("a permission granted mid-session reaches the FAB").

**Space for the button.** It covers the bottom `kFabClearance` (56 + 16) of the body. The Scaffold measures its margin from the bottom safe inset, and the body's `SafeArea` has already removed that inset. So `MobileDashboardBody.fabClearance` pads the list's bottom edge by exactly that, and the last panel can scroll clear. That constant used to live here as `kDashboardFabClearance`; invoiceninja/flutter#167 found the identical bug on every entity list and the three custom Tasks views, so it moved to `lib/ui/core/utils/fab_clearance.dart` with a `fabScrollClearance(context)` sibling for the surfaces that have no `SafeArea` of their own and must carry the inset themselves. The dashboard still adds the bare constant to its own gutter, because applying the inset on top of a `SafeArea` that already removed it would leave a visible band. `docs/pane-width-and-overflow.md` § A floating button is a bottom inset has the arithmetic.

**The timer pill had to move.** A phone in landscape is a railed shell (window ≥ 600) with a narrow dashboard (`Breakpoints.isPhone`). The railed branch pinned the pill at `bottom: 16`, which is the FAB's corner, and it paints on top. The 600–832 px window band had the same overlap with every list screen's FAB. `runningTimerPillBottom` returns 112 (margin + 56 + a 40 px gap) whenever the device is a phone or the pane is narrow. The railed branch measures the pane as the window less the rail, inside a `ValueListenableBuilder` on the collapse toggle. `running_timer_pill_wiring_test` keeps both branches on the rule, because `ScaffoldWithNav` cannot be pumped. It is still open for the three custom Tasks views: they show a FAB on a wide desktop pane, where the pill keeps the corner. That is not an oversight in those views, though — `buildTasksViewAppBar` renders no create action in either branch, so the FAB is the only way to start a task from Daily / Weekly / Calendar and cannot simply be gated away (#167).

**Why Reports went with the tiles.** The issue named New Client and Enter Expense. With both moved into the sheet, the row would have held one full-width Reports tile. That tile never checked `view_reports` or showed the plan lock, both of which the main menu's Reports row does, and that row is where Reports stays.

**The app bar's title.** The bar has one action now (Customize), so the title has room on every handset; `titleSpacing: 0` stays, and `dashboard_mobile_app_bar_test` still measures the word at 320 dp. Under the title sits the freshness stamp, the one place a phone says how old the page is. Two lines in a 56 px toolbar fit at the default text size and not at 140%, where the page name lost its top; past 1.3× the pair is scaled down together inside an explicit `kToolbarHeight` bound (the toolbar lets its title be taller than itself, so an unbounded `FittedBox` has nothing to fit to), in a box widened by the same factor so each line still ellipsises on width.

## A chart's callbacks are State tear-offs

**The Cash flow chart's fl_chart callbacks are methods on a `State`, never closures written in `build`.**

fl_chart's charts are implicitly animated: each restarts its tween whenever the data it is handed is not equal to the last. fl_chart includes every callback in that equality — `getDrawingHorizontalLine` in `FlGridData`, `getTitlesWidget` in `SideTitles`, `getTooltipItems` and `getTooltipColor` in `LineTouchTooltipData`, `touchCallback`, `distanceCalculator` and `getTouchedSpotIndicator` in `LineTouchData`, `checkToShowDot` and `getDotPainter` in `FlDotData`. The first line chart this card drew built five of them as closures in `build`, and a closure is a new object each time, so the data never compared equal: every rebuild of the card re-ran the 250 ms tween across every series with nothing different on screen. The card rebuilds several times while the dashboard loads (a section landing, a refresh starting and ending, a session notify).

`_CashFlowLineChart` is a `StatefulWidget` for that reason, and because it owns which slot's tooltip is open (below). A tear-off of a method on one `State` compares equal from build to build, and the methods read their inputs — tokens, formatter, currency, slots — live off `widget`. Three details that are easy to undo:

- **`borderData` carries `tokens.border`.** It draws the solid baseline, and it is also the only place the grid's token reaches the compared data: the grid colour comes from a callback fl_chart cannot see inside, so without it a palette change that left every line's colour alone would compare equal and never repaint the grid.
- **fl_chart always animates the first update after mount.** Its initial tween ends on the raw data, while every later target is that data with the axis bounds filled in, so the two never match. Equal data means no tween only from the second update on — a test that checks the first one proves nothing.
- **Opening or closing a tooltip is a rebuild with `Duration.zero`** (`_touchOnly`). The open slot is part of the data (`showingTooltipIndicators`, each line's `showingIndicators`), so a hover is a data change; at 250 ms the tooltip would trail the pointer. `didUpdateWidget` clears the flag, so new data still animates.

`chart_card_test` › an unchanged rebuild pins it with a control: the same sequence with one inline callback does re-animate, so the passing case cannot go vacuous if fl_chart changes what it compares. The same closure pattern is still in `reports_chart_card.dart`, `project_burnup_chart.dart` and `project_progress_card.dart`, which rebuild far less often.

## The needs-attention band leads both layouts

**Above it, for a new company only: the setup checklist.** `DashboardSetupChecklistSlot` is the first child of both bodies — one child always, like the band's slot — and while it leads a company with no invoices the zero figures and empty panels step back (`HiddenEmptyPanelsBuilder.force`). docs/first-run-welcome.md.

**The band is pinned to the head of the page on the wide and the narrow body alike — its lists side by side on a wide screen, tabs that switch rows in place on a phone — and "nothing to show" is a verdict over every bucket, computed once, in the view model.** It replaced the wide grid's Past Due panel (below the chart, behind a large empty state) and the phone's "Needs your attention" card (under the metric cards, ~690 px down). The figures and the chart describe a period; the band describes *now*, which is why it ignores the date range and why it comes first.

**Three buckets, all from lists the dashboard already downloads** — no request of its own (`helpers/needs_attention.dart`, pure, with `today` passed in):

- *Past Due* — the past-due section's rows, most overdue first (the server's order).
- *Due Soon* — upcoming invoices with something falling due within `kAttentionSoonDays` (7), soonest first.
- *Quotes Expiring* — sent quotes whose valid-until date is within the same window.

A list that is `null` has not loaded and contributes nothing: the band never calls a bucket empty on the strength of a fetch that did not answer, it simply has no tab for it yet. A bucket with no rows has no tab either. `invoices` / `quotes` are the module-and-permission gates — a company that switched quotes off still has quote rows on the server.

**On a wide screen the lists sit side by side — there are no tabs to switch.** Every list that has something is on screen at once, each under a header carrying its name, its count, the proven past-due sum (for Past Due) and its own "View all". As one tabbed list the band was three short rows stretched across 1,160 px — two large gaps a row, and the Remind button about 700 px from the name it acted on — under a tab strip that was a full row holding one chip, over a footer that was a full row holding one link. That was the first thing said about the finished dashboard: "too much empty space here".

**Columns stay narrow, and a list with more rows than fit takes more of them** (`attentionSlots`, `helpers/needs_attention.dart`, pure). The band has `attentionMaxSlots(width)` equal columns — one per `kAttentionMinColumnWidth` (300 px), never more than three. Each list starts with one; a spare column goes to whichever list is tallest for the columns it has (the earlier on a tie), as long as it has a row to put there. So three lists take one each; "4 past due + 6 quotes" is one column and two; one list of six runs three columns of two. Rows fill column by column and balanced (`attentionFlow`), so the most urgent stay on the left and three rows are one line of three, not three beside two empty columns. **A column no list can use is left empty rather than shared out** — one overdue invoice keeps one column's width, because widening is exactly what separated a row's buttons from its name. Up to `kAttentionRows` (3) rows a column, so up to nine on screen; the old "a taller window shows five" rule is gone, since five stacked rows a column pushed the figures off the first screen.

**The rows in those columns are the *stacked* form** (`DashboardRecordRow(stacked: true)`): identity and amount on the first line, status and **every** action — as icons with tooltips — on the second, under the amount. It holds from 300 px, so a row does not change shape as lists come and go beside it, and a row's second line is the action box's height whether or not its list has actions: at the default text size the row's floor alone would keep neighbouring columns in step, but at 140% the first line outgrows the floor, and only that fixed second line does (`needs_attention_band_test` "rows line up across columns", run at both sizes).

**The column dividers are an overlay in a `Stack`, not `IntrinsicHeight` + `VerticalDivider`.** A divider as tall as the tallest column needs that height before layout, and asking for it means every descendant must answer an intrinsic-size query — the way the chart's row came to paint nothing (§ The chart draws the grouping that fits). The `Stack` sizes itself to the columns and the positioned overlay fills it.

**Where columns do not fit it is tabs, and a tab is not a link** — the phone (`compact: true`, always), a pane with room for fewer than two columns, or more lists than columns (three lists under 900 px). Tapping "Due Soon" swaps the rows, so what is due this week can be acted on here; "View All (N)" leads to the filtered list for the rest. The tallest tab sets a `minHeight` (`min(rowLimit, tallest) × dashboardRecordRowExtent`), so switching to a shorter tab does not pull the page up under the pointer — `needs_attention_band_test` "switching to a shorter tab does not move the page". The phone shows one action a row; the footer carries the proven sum and "View All (N)"

**The band claims only what it knows.**

- **A count is the server's.** `DashboardRows.total` carries `meta.pagination.total` from the list fetch (`dashboard_api.dart` used to discard it); the cache payload became `{rows, total}` with a tolerant decode of the old bare list — JSON in an existing column, so no schema change. With no total, a short page is exact and a full page of `kDashboardListPageSize` (50) reads "50+" (`AttentionCount.exact`).
- **The past-due sum is shown only when proven**: every past-due invoice is in hand (`isCompleteList`) *and* they share one currency. A sum over the first fifty of eighty, or of pounds and euros together, looks like a fact and is not one. A row with no currency of its own is in the company's, so a client with no override and one explicitly set to the company currency count as the same.
- **Days late and the late amount use the client screen's rule** — `lateAmount` (`lib/domain/clients/client_past_due.dart`), which knows a deposit can be late while the balance is not. The two screens cannot disagree about what "past due" is.
- **The label is `past_due`, never `overdue`** — the French bundle renders that key "unpaid".

**Emptiness is the view model's, over every bucket** (`_syncAttentionEmpty`): past-due's entry in `emptyPanels` means *all three buckets are empty and the past-due list has loaded*. It used to mean the past-due list alone, so a phone hid the card while an invoice was due tomorrow, and "N empty panels hidden" counted a band that had something in it. When there is nothing: a phone (hiding empty panels) draws no band at all; the wide body draws one slim line — "Nothing past due · Next due: 0045 · Acme · due in 3 days" — because a good day should cost the page almost nothing and still say what comes next.

**The slot is one child, always** (`DashboardAttentionSlot`). Both bodies are `ListView`s, which match unkeyed children by index: a slot that came and went would shift, and rebuild, everything below it (§ An empty panel is dropped from the list). So the gap rides inside the slot, and "not shown" is a zero-size box in the same position — `mobile_dashboard_body_test` "the chart keeps its element when past-due empties out".

**One thing overrides a hidden band: a change that failed to save.** "2 changes could not be saved · Review" (`Services.watchOutboxAttention`) is the band's first line and opens the Outbox. It is not about invoices and must not disappear with them, so the slot stays open for it even when the user has switched the band off or it is empty; then it sits over the quiet line, never over rows the user chose to hide. The stream is built once in `initState` — one made in `build` re-subscribes on every rebuild.

**Pinning clean-up.** `_hydrate` moves `pastDue` to index 0 *before* it places missing kinds; `reorderPanels` and the Customize sheet's `mobileLayout` parameter are gone (the sheet shows past-due as a pinned header row on both layouts). `dashboard_panel_wiring_test` asserts both bodies mount `DashboardAttentionSlot`, still honour `_panelVisible(DashboardKind.pastDue)`, and do *not* also register past-due as a grid panel.

## A band action runs on a fresh record, never on the row

**A row is a cached copy of the server's list, so Remind / Payment re-read the record first and act on what it is now** (`_DashboardScreenState._actOnInvoice`, `_remindQuote`). Between the fetch and the tap an invoice can have been paid — in the portal, by a colleague, on another device — and the old `⋮` on these rows was a bare icon that only opened the record.

The order, each step there for a failure that happened without it:

1. **`unsavedChangesGuard.confirmIfDirty`** — every destination is in another branch, and branch state survives a switch.
2. **Busy on the button** (`DashboardRecordRow` owns it, per action index): the fetch takes a moment and a second tap must not fire twice.
3. **`invoices.refreshByIds` + `clients.ensureLoaded`, then `invoices.watch(...).first`** — the real `Invoice`, with its invitations and its client's contacts on the device.
4. **`invoiceVerdict` / `quoteVerdict`** (`helpers/attention_record_verdict.dart`, pure): `resolved` (paid, cancelled, reversed, deleted, or a zero balance whatever the status says) toasts "no longer owed" and refreshes the band so the row goes; `unavailable` (not on the device and not fetchable — offline) says so rather than opening an empty screen; `act` continues.
5. **`findActionItem(InvoiceActions.itemsFor(...))`** — the tap re-checks against the same gate the record's own menu uses, then runs the existing action. No second definition of "may this user do this".

**Remind opens the reminder, not the first-invoice email.** The email route takes `?template=`, and the band passes `nextInvoiceReminderTemplate(row)` — `reminder1` / `2` / `3` by `remindersSent`, then `reminder_endless` — or `kQuoteReminderTemplate`. `BillingDocEmailScreen.initialTemplate` is honoured **only when it is one of the document type's own templates**; anything else falls back to the first, silently, which is the initial-invoice email — exactly what a Remind must not send. So `needs_attention_test` asserts every id the band can produce is in `BillingEmailTemplate.forType`.

**Which buttons a row gets is decided per row by the host** (`AttentionActions`): `create_payment` for Payment; `AuthSession.canEditRecord` *and* `maySendEmails` for Remind. The band knows nothing of sessions. A button is drawn on every row of a tab or on none — a row that may not do what its neighbours can keeps the slot, invisible and inert (`Visibility(maintainSize:)`), so amounts stay in one column.

**`maySendEmails` (`AuthCompany`, `!can('disable_emails')`) is new, and every Send Email action now asks it** — invoice, quote, credit, purchase order (a recurring invoice has no Send Email: the server never emails one, invoiceninja/invoiceninja#13368). `SendEmailRequest` refuses a holder of that token before it looks at the record, so the action used to open a screen whose Send could only fail. It is a *negative* token (`kPermissionNegative`): the admin's blanket grant must not confer it.

## Unknown is not zero

**A figure that has not loaded is a placeholder, one that could not be loaded is a dash with a retry, and only a loaded zero is `$0.00`.** The old KPI row formatted `amount ?? Decimal.zero`, so "not loaded yet" and "failed" both read `$0.00` — an answer, and a wrong one. The chart said "No data for this period" while it was still loading (nothing ever put its section into a loading status, so its skeleton was unreachable), and a failed refresh printed "Not yet loaded" over a page of cached numbers.

`ValueSectionState` (`view_models/async_section.dart`) is the vocabulary, read off any `AsyncSection`: `loading` (no data, no error) · `failed` (error, nothing cached) · `stale` (error over cached data — the figure is real but not current) · `ready`. `FigureValue` draws a bar, a dash, or the number; the card offers Retry when failed and a `sync_problem` glyph when stale. The chart reads the same four.

Three things in the view model make the states true:

- **A filter change resets `totals`, `totalsPrevious` and `chart` to idle.** They are keyed on the filter hash, and the old window's figures (and its error) belong to the old window; without the reset a new range showed last range's numbers until its own arrived.
- **A totals failure is filed on `totalsPrevious` too.** One job fetches both windows and reports under one kind, so the comparison would otherwise never learn it failed.
- **`figuresFetchedAt`** (the totals cache row's write time) feeds `freshnessText(cachedAt:)`, so a failed first pass over cached figures says how old *those* are.

**A figure's caption shrinks to fit, like the figure — neither is ever ellipsised.** Three cells across a phone at 140% text leave a caption about 75 px, and "RECHNU…" over a number does not say what the number is (`_FigureCaption` is a `FittedBox(scaleDown)`).

**Skeletons are drawn in `tokens.border`.** `surfaceAlt`, which they used, is 1.04–1.22:1 against a card — a placeholder nobody could see.

**A quiet period is not a failed one.** The chart's axis is zero-filled across the window, so "nothing happened" has to be read off the points, not the lanes: a loaded series with no points says "No data for this period" rather than drawing a row of empty slots. (`chart_card_test` "a series that loaded with nothing in it says so" — it caught exactly that regression while this was being built.)

**Users without `view_dashboard`** are refused the chart endpoints by the server, so the period row, figures, metric cards and chart are not drawn for them (`_showsFigures`); the band and the list panels, which come from ordinary list routes, remain.

## Outstanding is as of today, and a trend compares like with like

**Outstanding is everything unpaid today — its own `totals_v2` call over an open-ended window, cached under `DashboardKind.totalsOutstanding` — and carries no trend.** The server's `outstanding` is `invoices.date BETWEEN start AND end` (`ChartQueries`), so under "This Month" the tile showed only what invoices *dated this month* still owed, and its "+298% vs prior" compared the unpaid remainders of two unrelated sets of invoices. **The window is spelled out (`kOutstandingWindowStart` 1970-01-01 to `kOutstandingWindowEnd` 2099-12-31, as `custom`), not the `all_time` preset — that one ends today.** An invoice dated next week and already sent is owed, and `all_time` drops it; measured on the demo account, whose seed data is post-dated, `all_time` returned 334.00 across one invoice while four were unpaid, 9,727.00. The first "after" screenshot showed exactly that figure beside a list of four. Fixed strings rather than offsets from today, so the request is the same from one day to the next. The watch is keyed on `includeDrafts` only, so a new date range neither refetches nor blanks it. Its footer is "9 unpaid · $3,400.00 past due": the count from the same response, the past-due figure by the band's rule, so the two agree (§ The aging bar is hidden, never zero, and past due is the band's).

**The chart has no Unpaid series.** The server's chart `outstanding` is still the period-scoped number — what invoices *dated in the window* still owe — and it was drawn as a third line named "Unpaid" so it would not be read against the Outstanding card. The bar chart (Cash flow: Invoiced, Payments, Expenses) dropped it: money moving in a period is the chart's question, and what is owed today is the card's.

**The period figures are Invoiced · Payments · Expenses** — one request, failing together. Invoiced and Expenses were in every totals response and shown nowhere, while the third tile was a count that repeated the first. Expenses is drawn only with the module on and is not a link (no ↗): the expenses list has no date filter it can show. **On a wide screen they are the cells of one card, each in Outstanding's own layout** (`PeriodSummaryGroup` of `PeriodSummaryCard`s over `_SummaryCard`: label with ↗ only on a link, value, footer pinned to the bottom edge) (§ The period figures share one card on every layout). Each footer is a filled `DeltaChip` (↑ / ↓ and the sign, never colour alone) and "vs {previous}"; a previous zero draws **no chip at all, just "vs $0.00"** (critique pass 2: the neutral "—" chip that stood there read as a missing value, and a rise from zero has no percentage worth inventing — `DeltaChip`'s filled form returns the suffix alone for a null percent; `kpi_row_test` "a previous zero draws no chip"), and "All time" has no footer. **On a phone they stay one card with three cells** (`PeriodFiguresCard`): three narrow cards stacked would push the chart a screen down. The figures' labels are sentence case now, matching the design, and a value renders through `LtrText`.

**A window still in progress is compared with the same elapsed span of the period before** (`DashboardFilterComparison.comparison`, `lib/data/models/value/dashboard_comparison.dart`). The trend used to compare the whole window with the same number of days shifted back, so on the 7th "This Month" set seven days of income against a whole month and every figure showed a steep fall until the month was nearly over. Now the 1st–7th is set against the 1st–7th — **and the current figure is the 1st–7th too**: `fetchTotals` sums the comparison's *current* window (`currentStart..currentEnd`, which ends today while the period is in progress), not the whole selected one, so a post-dated invoice leaves "This Month · Invoices" until its date instead of inflating the trend against a previous span that stops at the same day. The drill-down lists (`_invoicedIntent`, `_paidPaymentsIntent`) take the same window, and an in-progress custom range names it in the period row (on the wide range button's dates segment, or "Oct 1 - Oct 18 vs …" in the compact caption) because the button's own dates do not. Calendar presets step back one calendar *unit* (month / quarter / fiscal year — "thirty days before September" starts on August 2nd); a rolling window or a custom range steps back by its own length; "All time" has no comparison and draws no trend at all. The period row names both windows once instead of each tile saying "vs prior". **Wide, the current window is the range button's second segment ("This Month ▾ | Nov 1 - Nov 17") and the previous one a dashed "Compare to Oct 1 - Oct 17" box beside it; Include Drafts is pushed to the row's trailing end.** The dashed box is a label, not a control — there is no compare picker, the previous window follows from the range — so it has no fill, no hover, no focus and no tap, and reads to a screen reader as one phrase (`DashboardCompareLabel`, pinned by `dashboard_period_bar_test` "is text to a screen reader, never a control"); the solid-outlined controls beside it are the ones that open something. The two halves sit in an `OverflowBar`, so a row too narrow for both drops the switch under the rest instead of leaving the start half to wrap in what a spacer left it.

**On the narrow layout the period row is controls, then one caption** (`DashboardPeriodBar(compact: true)`, passed by the host). Inline, each control with its note beside it is too wide to share a phone's row with the next, and the block came to three 44 px rows; compact, the range, currency and drafts controls share a wrapping row and "Oct 1 - Oct 7 vs Sep 1 - Sep 7 · Converted to USD" is a single line under them. The conversion note is said once, here, beside the currency control — it used to be repeated under each figure card and again in the chart.

**Every preset except all-time is sent as `custom` with the app's own dates.** `MakesDates::calculateStartAndEndDates` recomputes the window from the preset *name*, and its idea differs from the header's: "last 7 days" is `subDays(7)`..today, which is eight. Sending the dates makes the server sum the window the screen names. **The figures run to today while the chart covers the whole window**: the chart (`fetchChartSummary`, `_windowBody`) and the configured cards keep the full range, so a post-dated invoice still counts there, and Outstanding has its own open 1970–2099 window (above), whatever the range. The calculated-field cards keep the preset name (`_periodBody`), because `calculatePreviousPeriodStartAndEndDates` returns the *same* window for `custom` — their "previous period" would be the current one (`BACKEND.md`).

## The period figures share one card on every layout

**Invoiced · Payments · Expenses are cells of one card beside Outstanding's own — never three cards of their own — and whatever the width or the module set, the ones drawn stay grouped; a lone one is just a card.** 5.1.30 drew them that way on desktop and phone; the 2026-11 redesign split the wide row into four equal cards, and Hillel's call comparing the two was "keep invoices, payments and expenses grouped together". They are one answer from one request (`DashboardKind.totalsCurrent`) that loads and fails together, so the group (`PeriodSummaryGroup`, `dashboard_figures.dart`) is one `_FigureSurface` with `VerticalDivider` hairlines in the `border` token, and **one retry, in the last cell's corner**. The other cells pass `retryPlaceholder`, which reserves the control's height (`_FigureRetry(placeholder: true)`) without drawing it — without that, the failed or stale state put the last cell's dash or value a retry-button lower than its neighbours'. Each cell is the very `PeriodSummaryCard` a lone figure is, with `framed: false`, so the cell and the card cannot drift apart.

The layout (`KpiRow`) has two units, Outstanding and the group. **They share a row when the row gives each figure `kFigureMinWidth` (220 px of the row's own width)** — `figuresShareRow`: 880 with all three, 660 with Expenses off — and the group's flex is its cell count, so a cell is about as wide as Outstanding and the eye still reads four even columns. Below that Outstanding takes a row and the group the row under it, **its cells still side by side** — the phone's form, and the wide body never measures under ~560 px (`Breakpoints.wide` less padding). The only figure a user can remove today is Expenses (module off, or no permission); the configurable cards (`ConfiguredCardsGrid`, `flutter_dashboard`) are a separate grid under the row and cannot hide a fixed figure. Tests: `kpi_row_test` "one row: Outstanding, then one card of three cells", "with Expenses off the two left stay grouped", "below the one-row width, the group takes a row of its own", "a failed fetch with nothing cached is a dash and a retry" (one retry, dashes on one line), group "a lone figure is just a card, with its own retry".

## The aging bar is hidden, never zero, and past due is the band's

**Under Outstanding sits what is unpaid today split by lateness — Current, 0 - 30, 30 - 60, 60+ days past due — from `POST /charts/analytics_totals`'s `aging` object** (`DashboardAging`, `selectAgingBuckets`), the same currency bucket the figure shows (`selectedCurrencyKey`: the converted `999` aggregate under "All currencies"). Probed on the demo server 2026-11-17: no `data` envelope, amounts are strings, a currency with nothing unpaid carries `{}`, and an aggregate over no rows carries nulls — all read as zero. The server's last three buckets (61–90, 91–120, 120+) are merged into 60+. The aging is a snapshot (`AnalyticsQueries::getAgingBucketTotals`): the window does not enter it and drafts are always left out, so its total can fall short of an Outstanding that includes drafts; the bar is a proportion, so that changes only the tooltip's sums.

**Cached in `dashboard_cache` under `DashboardKind.aging` / `kDashboardAgingHash` — JSON in the existing table, so no schema change.** One row per company, keyed by nothing in the filter: refreshed by every full pass (`refreshAll`), never by a filter change (`refreshFilterKeyed`), watched once.

**The bar is shown only while its section holds data.** Loading, failed, and a server without the endpoint all leave it out — never a zero bar, never a retry: it is an optional decoration of a figure that has its own retry. An older self-hosted server answers the missing route with 404 (400 / 405 on some stacks); `refreshAging` caches that as `DashboardAging.unsupportedMarker` instead of failing, and asks again on the next refresh so an upgrade is picked up. Any other failure is filed on the aging section alone, and `_runRefresh` takes it out of the pass's errors: no refresh toast, and "Updated just now" still moves (`dashboard_view_model_test` "a failure is filed on it and never fails the pass").

**One hue darkening with age, then amber and red.** Current is `partial`; 0 - 30 is a darker, greyer step of the same blue (derived in `agingSegments`, not a new colour); 30 - 60 is `warning` and 60+ `overdue`. 8 px tall, 2 px gaps, a 2 px radius — never a pill. A non-empty bucket is never thinner than 1.2 % of the strip. **It mirrors in RTL:** it is a part-to-whole proportion read from where the language starts, not a time axis, so Current sits at the start edge.

**Details: a tooltip with a pointer, a sheet on touch.** Hovering or focusing the bar lists every bucket; with a pointer a click still falls through to the card's link. On touch the 8 px strip sits in a 44 px tap band that opens `AgingBreakdownSheet` (each bucket's tone, share and amount, on the root navigator so Android back closes it). For a screen reader the card's label lists every bucket ("Aging: Current $24,310.00, …") and the breakdown is a custom action.

**What the footer calls past due is the band's definition, and agrees with it** (`outstandingPastDue`, `kpi_row.dart`): (1) the band's proven sum when it is in the figure's currency — the band prints the same number; (2) nothing when the band has loaded and is exactly empty; (3) else the aging's late buckets, when the band cannot prove a sum (more than a page, or mixed currencies); (4) else the band's count, "4 past due". The design's "past 30 days" was dropped: past due means past its due date, as everywhere else in the app. The one case (3) can differ from the band's rule is a late *deposit* on an invoice whose own due date is ahead — the server buckets it as current — which is why (1) wins whenever it exists.

## The figures are refetched when a change leaves the outbox

**The dashboard's numbers are server-computed and cached in `dashboard_cache`, so nothing in Drift moves when the user enters a payment from the band — the view model refetches on the falling edge of the outbox's active count.** `OutboxDao.watchActiveCount` counts `pending` + `in_flight`; `DashboardViewModel._onOutboxActive` schedules the same trailing, quiet refetch the realtime push uses (`_scheduleQuietRefetch`, `kAppliedChangeDelay` 1.5 s) whenever the count *drops*, and restarts it on a further drop so a burst is one fetch.

Why this signal and not the two obvious ones:

- **`watchPendingCount` falls when a row merely goes in-flight**, i.e. before the server has it — a refetch then reads the old figures.
- **`refreshRelatedEntities`** (where an applied mutation refreshes its neighbours) misses emails, plain edits and mark-paid, all of which change what the band shows.

It never fires on navigation or from the tap itself, and it never toasts. `dashboard_panel_wiring_test` asserts the screen passes `outboxActive:` — without it every test still passes and the band keeps showing an invoice the user just settled.

**A new calendar day is the other trigger.** A period in progress is fetched to *today*, but its cache key (`filterHash`) names the whole period, so "This month" on the 15th reads the row fetched on the 14th. The key stays day-free on purpose — keyed by day, the dashboard would open blank every morning offline — and instead `_checkDayRollover` polls every `kDayCheckInterval` (10 min) once the boot refresh is in, and on a changed `_today()` notifies (captions, the band's "N days late") and runs the same quiet refetch. Polled, not a timer aimed at midnight: a suspended app's timers stop with it, and a periodic one fires on its first tick after waking. Pinned by "a dashboard left open past midnight" in `dashboard_view_model_test`.

## One row grammar for every list

**Every list on the dashboard — the band and each panel, on both layouts — draws its rows with `DashboardRecordRow`: `number | client | when | status | amount | action`, one tap target that opens the record.** It replaced six-column `DashboardEntityTable`s in which every cell was its own target (about thirty tab stops a panel), whose intrinsic-width columns could not shrink into a half-width card, and whose last column was a `⋮` that opened no menu.

- **Anything else a row can do is an icon button on it** (`RecordRowAction`, with a tooltip that is also what a screen reader hears): Payment on upcoming invoices, Remind on upcoming quotes, nothing on rows where nothing can be done. There is no labelled form any more — the only place wide enough for one was a single list across a whole desktop, which is the layout that put the label 700 px from the name.
- **`compact` is passed by the host, never measured.** The rows sit in grid rows laid out with `IntrinsicHeight`, where a `LayoutBuilder` cannot be used; the narrow body passes `true`, which stacks the row to two lines and keeps one action.
- **The same card serves both layouts.** `_mobileListCard` and the `Mobile*Row` list rows are gone; the phone uses `UpcomingInvoicesCard(compact: true, preview: 3)` and its siblings, so there is one set of loading / empty / failed states (`DashboardPanelMessage`, `DashboardPanelError`) — one line each. They were an `EmptyState` with a 64 px icon and an `ErrorView` in a fixed 200 px box it did not even fit.
- **The wide form is a table row: a 64 px muted-mono number, then three parts client to two parts date, then the status column (on a mixed list) and a 104 px amount.** The number in its own fixed column puts every client at one x, which is what a reader scans down. At 5:4 with a 112 px amount, a half-width card on a 1280 px laptop cut the client's name while the date column had room to spare; 3:2 gives the rest to the name.
- **Each wide cell may carry a muted second line, and the floor already holds two** (`subline` under the date, `clientNote` under the client, `amountNote` under the amount; line heights are fixed so the sum is known, `_kTwoLines`). Rows with and without second lines sit in one card and beside the panel next to it, so a second line must cost no height. The phone keeps its two lines — the `subline` rides the date's line, the notes drop — and so does the Compact density's wide row, which stays 32 px.
- **A payment applied to one invoice names it under the client — "for invoice 0011" — only when that invoice is in Drift** (`PaymentInvoiceNote`, from `DashboardPaymentRow.invoiceIds`, the payment's `paymentables`). No request per row, never a hashed id, and nothing for a payment split across invoices, where one number would name a part as the whole. Payment amounts are ordinary ink: no "+", no green.
- **A row with a button is exactly as tall as one without** (`dashboardRecordRowExtent` = the action box + the row's padding, and the button sits in a fixed `SizedBox`; under Compact both shrink together — the floors live in `dashboard_density.dart`, see `docs/list-density.md` § The dashboard). Material adds to an icon button's footprint by platform density and tap-target padding; left to it, button rows came out 3 px taller, and two panels side by side were visibly out of step by the fifth row.
- **The Invoices & Quotes panels' date slot says which date it is** (`pipelineRowLead`): an open invoice its deadline, "Due Dec 17" (`due_on_date_label`; the deposit's due date while one is asked for — the date the late sub-line counts from); a paid invoice "Paid Nov 16" (`paid_on_date_label`) when the device holds a payment for it — its latest live payment's date, one Drift read per paid row (`latestPaymentDate`, looked up once per panel), never a request; a quote out with the client "Valid until Dec 14" (`valid_until_date_label`, the quotes list's own wording — the design's "Exp." abbreviation does not translate); anything else its document date as before. Short dates (`Formatter.dateShort`) within the current year, the company format outside it. The relative sub-line rules (near or late only) are unchanged. `billing_pipeline_card_test` › the date slot says what the date is.
- **A slot with nothing to say is empty, or says so in words — never a dash.** The "when" slot is unlabelled, and § An empty value is an em dash in a labelled slot applies. The server's "upcoming" includes a sent invoice with no due date at all (every one on the demo account is), and that row reads "No due date set": it is owed with nothing chasing it.
- **A one-line state is centred when the card is stretched.** In a paired row a card takes its row-mate's height, and "No upcoming recurring invoices" sat at the top of a hollow 440 px box beside the task calendar. `DashboardPanelGrid` wraps each paired cell in `DashboardPanelCell(stretched: true)`; the list card (and the activity card beside the chart) reads it and passes `DashboardCardShell.bodyFills`, which gives the body the card's remaining height. It is opt-in and comes from the grid because only the widget that builds the row knows the height is bounded — the same card in a full-width row or the phone's list has an unbounded one, where a flex child throws.
- **"View All (N)" carries the server's total** (`viewAllLabel`), and each link lands on what the panel shows: upcoming invoices → unpaid, due today or later; upcoming quotes → sent and not yet expired; recurring → the Active tab.
- **Upcoming invoices and quotes are sorted soonest-first in the repository** (`_soonestFirst`, undated last). The server's `orderBy` sits inside a nested `where` closure, which Laravel drops, so the five rows shown were the five created most recently (`BACKEND.md`).
- **A quote's valid-until date is `due_date` on the wire.** The row read `valid_until`, a field `QuoteTransformer` never sends, so Expired Quotes' "Valid until" column was all dashes.
- **A payment names its status only when it is not Completed** — a "Completed" pill on every row hid the one that was not.

## Which panels share a row is one function

**`layoutPanelRows` (`helpers/panel_rows.dart`, pure) decides the rows; `DashboardPanelGrid` only draws them.** Filling two columns in order left a lone panel beside an empty half whenever the count was odd, and put the widest panel in half a row.

- **Panels pair up**, in the user's order.
- **An odd count gives a list panel the row** (the last panel at an even index that may span), so everything else pairs.
- **A spanning list panel flows its rows into two columns** (`DashboardRecordRows`, reading `DashboardPanelCell.spans`, which the grid sets only in two columns), the earlier half on the start side, with a full-height divider drawn as an overlay. One row stretched across the page is the gap the Invoices & Quotes split removed, and with Hide on every panel and empty panels hidden on phones an odd count is common. `dashboard_record_rows_test` pins it.
- **`kNeverSpanPanels` keep their half**: the task calendar (its month grid is an island across the page) and the Invoices and Quotes panels (a status strip in one corner). When no panel at an even index may span, the last keeps its half.

`panel_rows_test` covers every subset; the grid's own test pins that it draws the answer and that a panel changing row or width keeps its element (the `GlobalKey` rule above).

**Two-up starts at a pane of `kDashboardTwoColumnPane` (1000 px).** It was 1200 — a 1432 px window once the sidebar is counted — so a 1280 or 1366 px laptop stacked every panel full width and the page ran to eight screens. At 1000 each half-width card has about 470 px, which holds the row grammar at the largest text size with the client's name still readable.

## The wide bar's creates are measured, and one always survives

**The wide layout's create buttons live in the fixed top bar — "+ Quote", "+ Payment", then the one filled "New Invoice ▾" split button, from `quickCreateEntities` in the phone sheet's order — and the bar serves its three tenants in a fixed priority.** A row of creates in the scrolling body is what the phone once had and lost (flutter#164): it scrolled away with the page. Up here they are on screen however far the dashboard is scrolled. They took the room of the date range, currency and include-drafts controls, which moved into the page (`DashboardPeriodBar`) to sit above the figures they change — in the bar they read as filters on the whole dashboard, and most of it ignores them.

**The first option is the primary, and it ends the run, outside the measurement.** It is the only filled control, it reads as the full phrase ("New Invoice"), and it sits in the corner a toolbar's primary takes; being outside the `OverflowView`, no squeeze folds it away — a squeeze drops the outlined secondaries first. **It is a split button, and its ▾ is the bar's only menu** (`_SplitCreateButton`: two filled halves of one rounded rectangle, start corners on the create, end corners on the ▾, a faint 1 px seam in the button's own ink; the ▾ is a `BackDismissibleMenuAnchor`). The ▾ lists **every** create but the primary, the visible secondaries included: there used to be a separate "⋮ More" button between the secondaries and the primary, listing only what had not fitted, so what it held changed with the window's width and the eye had two places to look for "the rest". Repeating Quote and Payment costs two menu rows and buys a menu that is the same at every width. **How many secondaries show is measured, not guessed.** `DashboardCreateStrip` is an `OverflowView.flexible` of at most two secondaries (`kDashboardCreateStripMaxButtons` counts the primary): as many as fit, and the overflow builder draws nothing — what did not fit is already in the ▾. The strip is capped at `kDashboardCreateStripMaxWidth`. No button in the run carries a `Tooltip` — `OverflowView` lays its children out inside a layout callback, where an `OverlayPortal` cannot mount; the ▾, outside the run, carries "More". A secondary's visible label is the bare noun; `Semantics` carries the full phrase the phone sheet uses. The phone keeps its `+` FAB and create sheet unchanged.

**The priority, when the bar is tight: Customize (never pushed off) → the company's name (up to 240 px) → the creates.** A plain flex row cannot say that — it shares the squeeze between the name and the buttons in proportion — so Customize is laid out first and a `LayoutBuilder` splits the remainder. And **the name gives up just enough for one `+`**: the wide layout has no create FAB, so below `dashboardCreateStripMinWidth` — the split primary (its label, chrome, seam and ▾), measured from the label at the current text size, because the primary is now a phrase and "Neue Rechnung" at 140 % is not "New Invoice" at 100 % — the strip collapses to a single filled `+` (`DashboardCreateMenuButton`) that opens every create. `dashboard_top_bar_test` "a long company name still leaves a create button"; `dashboard_create_strip_test` "the floor it reports holds the split primary", "the ▾ lists every other create, in order, whatever fits", "there is no More button and no horizontal ⋯".

**Refresh rides the freshness line; Customize is a quiet icon at the trailing end.** Refresh is a 24 px icon button (the touch target on touch, density pinned to `standard` so the desktop theme's `compact` cannot take 8 px off it) at the end of the "Updated just now" line under the company's name — beside the stamp it renews, rather than as one more labelled button between the user and New Invoice. Its tooltip is its screen-reader label. Customize (`DashboardCustomizeButton`) is a borderless tune icon behind a rule, last in the bar: the design mock drew it first, but it is a page setting reached now and then, and a fixed trailing control keeps the measured create run in one piece. The title is the app's one page-title size (18 px semibold), not the mock's 20.

## The chart draws the grouping that fits

**The Cash flow chart draws the nearest grouping that has between four and 31 slots, and its Day / Week / Month control shows the grouping in effect.** One month grouped by month is a single slot — a figure the cards above already state — and a year by day is 365 points in a hairline. `buildChartAxis` steps month → week → day while there are fewer than four slots and day → week → month while there are more than `kChartMaxBuckets` (31, a month by day); `ChartAxis.grouping` reports what was built, and `chartGroupingFits` disables the segments that cannot draw the range. When even months are too many — "All time" is a fifty-year window — the axis starts at the first month with data, not in 1976.

**A slot is a period, not a boundary.** The line chart plotted the web client's boundary dates (`useGenerateWeekDateRange`), where the first point is the window's first day alone and each later one sums the days since the previous boundary. Drawn as slots, that made the first one day wide beside week-wide ones — an invoice dated the 1st became a lone spike. `chartPeriods` cuts whole days, weeks (from the company's `first_day_of_week`) and calendar months, clipped to the window only at its two ends, and every slot keeps its width when it is empty, so the spacing of the points is the spacing of time.

**It is a line chart again, drawn so a lone value reads as a spike in its own slot** (Hillel preferred lines to the bars of the Nov 2026 redesign; `_CashFlowLineChart`). The old line chart joined sparse daily points corner to corner, so a single payment read as a slope across its neighbours — a triangle of money on days that had none. Now **every slot has a point at its centre** (`buildChartAxis` zero-fills the lanes; the x range runs from −0.5 to n − 0.5, so the first and last points are not jammed against the axes), **an empty slot's point lies on the baseline**, the segments are **smooth but never overshoot** (`isCurved: true`, `curveSmoothness: 0.3`, `preventCurveOverShooting: true` — Hillel asked for the 5.1 chart's curves back; without the overshoot guard a spline dips below the baseline between a spike and its zero neighbours), and **only a point with a value gets a dot** (`checkToShowDot`, a 3 px dot ringed in the card's surface). No area fill. The old chart's fourth series, Unpaid (`ChartSeriesId.outstanding`, `tokens.sent`), stays dropped: restoring it means re-adding the enum value, its legend toggle and its persisted selection, and its meaning ("what invoices dated in this period still owe") was the one users read as contradicting the Outstanding figure. `chart_card_test` "an empty slot is a point on the baseline, with no dot".

Also true of the card now, each with a test in `chart_card_test`:

- **One headline, "Net received", and no totals in the legend.** It once led with the period's paid revenue — the Payments figure directly above it, again — and the design's legend chips carried each series' sum; both are left out for that reason. Payments less expenses is the one number the cards above do not state, so it is the headline (`_netReceivedLine`, above the legend): **computed from the figure cards' own totals** (`netReceived` over the bucket `selectCurrencyTotals` picks for the selected currency), never from the chart's series, which come from another endpoint and could disagree with the Payments and Expenses cards by a late payment. Without the expenses module it is the payments, under the same label. **Hidden while the totals are loading or failed with nothing cached** (unknown is not zero), shown over a stale cache as the cards are. Green (`paid`) above zero with a `+`, red (`overdue`) below with the formatter's minus, plain ink at zero; the amount is an `LtrText` in the money face. `chart_card_test` › Net received.
- **The time axis ends at today.** "This month" on the 17th used to draw every week to the 30th, the last ones blank. `buildChartAxis(today:)` drops the empty slots after the current one and clips the current slot to end on today (its tooltip reads "Nov 15 – 17"); past empty slots keep their place, a point dated after today (an invoice dated next week) keeps the axis running to it, and a window wholly ahead or already over is drawn as asked. **The grouping is still chosen on the whole window** — trimmed first, "This month" by week would refine itself to days until the 22nd. No projected or scheduled slot (declined). `chart_series_math_test` › the axis ends at today; the widget passes `Date.today()`, so a chart-card fixture must sit in a window already over.
- **Beside the activity feed it fills the row's height** (`fillHeight`), so the two cards end on one line with their contents, not just their borders. Stacked, it keeps its 2.4 aspect ratio above a 200 px floor (`kChartStackedMinPlotHeight` — a phone's width over the ratio is ~120 px). **The plot is a `Positioned.fill` child of a `Stack`, and that is load-bearing:** the row is an `IntrinsicHeight`, and fl_chart's plot is a `LayoutBuilder`, which throws when asked for an intrinsic size — the whole row then painted *nothing*, a blank band under the figures, with every widget test green because they handed the card a tight box. A `Stack` measures only its non-positioned children, so the row sees the floor (`kChartMinPlotHeight`) and the plot is never asked. The fixed aspect ratio it replaced hid the same problem by never asking its child either. `chart_card_test` now pumps the card inside the screen's own `IntrinsicHeight(Row(stretch))`, and fails with "LayoutBuilder does not support returning intrinsic dimensions" without the `Stack`.
- **The legend entries are real toggles** — `ChartLegendToggle(chip: true)`, an `InkWell` with `Semantics(toggled:)` and the 44 px touch floor; they were 8 px dots in a bare `GestureDetector`. **The last series shown cannot be switched off**: the view model refuses an empty selection, but a non-empty one can still draw nothing here (Expenses alone, then the module goes off), so the card guards what it draws, and a selection with nothing to draw says "No series selected". Expenses is neither drawn nor offered without the module (`expensesOn`).
- **Series colours are fixed status tones** — invoiced `partial` (blue), payments `paid` (green), expenses `ink3` — never the user's accent: a green or red accent collided with Payments or read as "overdue".
- **Axis ticks are short dates with the month as a word; the tooltip uses the company's full format.** A day reads `Nov 12` (`Formatter.dateShort`), a week its first day, a month `Nov` — `Nov 2026` when the axis crosses a year (`Formatter.dateMonth`). The company format (`11/12/2026`) does not fit under a slot, and a bare `11/12` reads as December to half the world. `chart_card_test` › dates.
- **The date axis labels as many buckets as fit, measured.** The cap was a fixed six; a phone drawing one month by week then had six `01/Oct/2026`-sized labels in 250 px, printed over one another — a regression the finer grouping introduced and the phone screenshot showed. `_CashFlowLineChartState.build` measures the widest tick at the user's text size and divides the plot's width by **one and a half** label widths (`_labelStep(maxLabels:)`, never fewer than two) — the first and last labels are pushed inside the plot (`fitInside`), so each sits half a width closer to its neighbour than the ticks are, and a bare width plus a gap let them touch at 140% text. The `LayoutBuilder` it uses is legal only because the plot's host never asks that subtree for an intrinsic size — see the `Stack` rule above.
- **The value axis is round amounts, short, on the right.** `chartValueScale` picks a 1 / 2 / 2.5 / 5 × 10ⁿ step with at most four steps, and the top gridline is the multiple just above the highest point, so every gridline is a labelled amount (`$20K`) — the line chart's top was the tallest point plus a tenth, an amount nothing on the chart was. Gridlines are dashed; the baseline is solid (the bottom border — fl_chart's grid stops short of both bounds, so the top is an extra line). This departs from `chart_chrome.dart`'s solid `chartGridLine`, which Reports and Projects keep. The time axis and the amounts stay physical in RTL (`// rtl: physical`), as in those charts.
- **The tooltip is the whole slot**: its dates in full (a day, or a week's or month's first and last day) and every visible series' value, whichever line is nearest the pointer. The built-in touch handling shows the nearest spots only while a finger is down, so `handleBuiltInTouches` is off and the chart's `State` owns the open slot (`LineChartData.showingTooltipIndicators` with the slot's spot on every line, and each line's `showingIndicators` for the hairline and dots): a mouse opens it by hovering, a tap opens it on touch and a second tap on the same slot closes it. Distance is measured on x only (`distanceCalculator`) with a `touchSpotThreshold` of half a slot, so the whole column is the target — a $5 point on the baseline is otherwise a 6 px target. fl_chart asks `getTooltipItems` for one entry per shown spot; the first carries the whole slot and the rest are null.

## The activity card reads who did what, under day headers

**Each row is the server's `activity_<N>` sentence with its values set apart, the actor's initials (with the tone icon as a corner badge), and a muted meta line; rows group under "Today" / "Yesterday" / the company date, and the whole row is the one tap target** (`ActivityCard`, `DashboardActivityRow`). The sentence comes from `ActivityFormatter` — the same template substitution the `/activity` screen uses, including the type-10 online/manual pick, the type-54 contact swap, the user-lifecycle (48–52) second slot and the call-note marker strip — which now also returns the sentence cut into `ActivitySegment`s (template words vs filled values) and the `tokens` it filled. The card draws the values in the strong ink; `buildActivitySpans` was not reused because it takes a record-tab `Activity`, links refs, and lacks the dashboard feed's lifecycle and call-note handling.

- **The actor leads as an `InitialsAvatar` seeded on the user's id** (`_ActorAvatar`), the same tint the user wears on every other surface, initials from the `:user` label (`initialsFor`, first and last word). The activity's tone icon rides the avatar's bottom-end corner as a 15 px circle (12 under Compact) ringed in the card's surface, so the verb's colour survives without a second leading column. A row with no `:user` label — a contact viewing an invoice, a system run — keeps the tone circle alone: there is nobody to draw, and a "?" tile would claim a person. `activity_card_test` "the actor leads as initials, the verb as a corner badge".
- **The meta line names what the sentence does not**: the client (else the vendor) when the template has no `:client`, else a `payment_amount` label the sentence does not show, then the relative time (`activityRelatedLabel`).
- **Days are calendar days through `Date`** (`activityLocalDay`, `activityDayLabel`), so a DST change cannot make yesterday today, and an older day's header is `Formatter.date` output — the card's `formatter` is required, so there is no ISO fallback.
- **"Carey Feest Danyka Terry created invoice 0026" was one person, not an actor and a client run together.** The `:user` label is `UserPresenter::name()`, `first_name . ' ' . last_name`, and the demo server's `UserFactory` seeds *both* with `faker->name()` — live, the demo user is `first_name` "Theron Hermiston", `last_name` "Dixie Schaefer". Nothing in the app joined two labels. The strong weight keeps a four-word name reading as one name, and the client now sits on the meta line, apart from it.
- **No inline link and no chevron** — § An inline link in a sentence cannot be hit by a finger. A row naming no record is inert. On touch a row is never under 44 px.
