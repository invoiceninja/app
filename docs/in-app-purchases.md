# In-app purchases

Companion to CLAUDE.md § Strict rules. How the store builds sell a hosted plan in-app and deliver it to the account: which builds sell, what the app waits for before it posts or finishes a purchase, which answers finish one, which key a purchase is posted under, and where the copy lives. The code is `lib/domain/upgrade/` (`store_build.dart`, `upgrade_route.dart`, `upgrade_launcher.dart`, `purchase_delivery.dart`, `purchase_service.dart`) over `StoreBilling` in `packages/store_services` (docs/fdroid.md for the FOSS twin).

## Store builds never link to an external purchase

A store build is `isStoreBillingBuild`: a store package build (`StoreReview.isStoreBuild`, false in the FOSS twin) on iOS, Android or macOS. Such a build may not send anyone to a purchase outside the store (App Store 3.1.1(a), Play Payments policy 4), so:

- `resolveUpgradeRoute` never answers `billingPortal` on a store build. A trial or a web-billed plan (`AuthSession.isWebBilled`) goes to the Plan screen, which says the plan is managed on the web, and every upgrade prompt (`PlanGateBanner`, `TrialFooter`, `PlanExpiredFooter`, the Plan card) shows that line with no button (`planManagedOnWeb`). A long-expired web plan has a blank slug and is a free account again: it is offered the purchase sheet.
- The white-label checkout, the PEPPOL credit packs and any off-origin page the DocuNinja embed hands over are refused when `isExternalPurchaseUri` says they sell something: Stripe's payment pages, the billing host (`kInvoiceNinjaBillingHost`), a client-portal subscription checkout, the pricing pages.
- Desktop, the web and the F-Droid / GitHub APKs keep the billing portal. An in-app plan is still managed only in its store there, and a lapsed one is not sold a web plan for `kIapRebuyAfter` (60 days) while the store may still renew it. An unreadable `plan_expires` (blank, unparseable, a pre-2001 sentinel) reads as long ago there (`iapPlanEndedLongAgo(ifUnreadable: true)`), or a legacy in-app account with a blank date could never reach the portal; a store build keeps the fail-closed reading, so it never sells a second store plan on a date it can't read.
- `upgrade_launcher.dart` opens a server-sent portal URL only when it is http(s) (`isSafeWebUrl`).

Tests: `test/domain/upgrade/upgrade_route_test.dart`, `test/ui/features/settings/widgets/plan_gate_copy_test.dart`, `test/ui/features/settings/views/basic/account_management/plan_hosted_actions_test.dart`.

## A store build shows no way to buy until the hosted config says it sells to the active account

The store apps may ship before the hosted billing (the admin-module purchase routes) is deployed. App Store 3.1.3(f) (a free stand-alone companion to a paid web service) and Play's Payments policy allow that only for an app with no purchase UI and no call to action to buy anywhere else: no Upgrade, Buy, Subscribe or Restore, no prices, no "upgrade on the web", no trial offer. An Upgrade that only answered `in_app_purchases_unavailable` would read to App Review as a broken purchase flow. So a store build decides per account whether it sells at all:

- **The predicate.** `inAppPurchasesOffered` (`upgrade_route.dart`): a store-billing build, a hosted session, and the hosted config (`GET kIapConfigPath`) answers `IapConfig.sellsTo` for it: `purchases_enabled: true`, a UUID `app_account_token`, the active account's `account_key`. No answer, an error, a 404 (production today: the route does not exist), `purchases_enabled: false` all read as no. The server also says no to a non-owner, a company of another account, and an account with a running store or web plan (`SubscriptionController::iapConfig` in admin-module), so the app cannot tell "switched off" from "not yours to buy": both are no.
- **Where it is asked.** `PurchaseDelivery` (store builds only) owns `offer`, a `PurchaseOffer` (`purchase_offer.dart`, a `ChangeNotifier`), provided at the root by `main.dart` and read as `PurchaseOffer?`. It asks once per signed-in user and active company (the same request and cache the delivery already uses), again when the account's store plan changes, and on a return to the foreground once the last answer is older than `kPurchaseOfferMaxAge` (30 minutes). It reads false the moment the user or company changes, until that one's own answer. A 404 (a server without the route, production today) is an answer, closed, and waits the full `kPurchaseOfferMaxAge` too. A failed ask (an error, no network) leaves the last answer for the same user and company standing (a flaky resume does not make the buttons blink) and is retried on a resume only after `kPurchaseOfferRetryAfter` (5 minutes): Face ID, Control Center and every share sheet are inactive→resumed round trips. There is no timer. An answer asked before a forget (a plan change, a resume) never overwrites a newer one. No screen asks anything.
- **Where it is read.** `purchasesWithheld(context)` (`upgrade_launcher.dart`) is `storePurchasesWithheld`: a hosted session on a store build without the offer. It is false off a store build and for a self-hosted server, and reads nothing there, so desktop, the web, F-Droid and self-hosted keep the billing portal exactly as before. Tests set `debugInAppPurchasesOfferedOverride` as they set `debugStoreBillingOverride`; with neither a provider nor the override a store build reads as not offered.
- **What a withheld prompt says.** Only which plan the feature or limit belongs to, with no button, and never `plan_managed_on_web` (on a locked feature, or under "plan expired", it reads as "go and upgrade on the web"; only the Plan card keeps it): the plan banner says `feature_needs_pro_or_enterprise` or `requires_an_enterprise_plan` (to owner and member alike, never "the owner can upgrade"); a refused paid setting's toast says the same; Reports say `reports_need_pro_or_enterprise`; DocuNinja says `docuninja_needs_pro_or_enterprise` with no Upgrade; its seat limit says `max_users_reached`; Tap to Pay on a lower plan says `terminal_server_plan_required` with Close only; document history keeps its subtitle without Upgrade; the expired-plan footer keeps its title without Pay Now; the trial footer drops its pitch; a free user's New design button is not drawn and a custom design row does not open the upgrade; New company on the Free plan's company limit is disabled and says `free_plan_company_limit_reached`. The client limit keeps every number (docs/free-plan-limits.md). The signup note leaves out "Upgrade any time" on every store build: there is no account to ask about yet.
- **The Plan tab.** The hosted Change Plan card is left out (`showsHostedActionsCard`) unless it has something to manage or explain: an active store plan keeps "billed through the app store" and **Manage subscription** (managing a subscription is not a purchase, and both stores ask apps to link to it), a lapsed one says `store_subscription_ended_info` without where to renew, a web-billed plan keeps `plan_managed_on_web`. Restore Purchases is not shown while the store is closed (below): nothing can have been bought in this app while it sells nothing, and a purchase left over from a sale switched off later is still delivered by the launch and resume sweeps.
- **The store being open is a second answer.** `purchases_open` (`IapConfig.purchasesOpen`, admin-module #38/#39) says whether the hosted service sells in-app at all, to anyone, and comes in every answer, the non-owner's `{purchases_enabled: false, purchases_open: true}` included. `inAppStoreOpen` reads it (or a sale to this account, `sellsTo`, which implies it on an older server without the field); absent, false, an error or a 404 is closed. `PurchaseOffer.open` carries it and `inAppStoreOpenIn(context)` reads it (`debugInAppStoreOpenOverride` in tests). Open but not offered to this account, a store build shows **Restore Purchases** to the owner (App Review requires a restore mechanism wherever subscriptions are sold, so an in-app subscriber, whose `purchases_enabled` is false, gets it too, and the Plan card is drawn for it), and a member gets the "the account owner can upgrade" copy (`owner_upgrade_to_paid_plan` on the plan banner, `terminal_plan_ask_owner` with Close only, `store_plan_owner_only` on the Plan card), still with no button. Closed, everything above stays withheld.
- **A store subscriber keeps the banner's button.** At an Enterprise gate an owner whose plan is a live store subscription (`UpgradeRoute.storeSubscriptions`) keeps the banner's button once the store is open: it opens the store's own subscription page, which manages a plan rather than selling one.
- **The server's "please upgrade" sentences.** On a store build `storeSafeServerText` (`lib/ui/core/utils/store_safe_server_text.dart`) says `LoginController`'s "Pro / Free accounts only the owner can log in. Please upgrade" as `owner_only_sign_in_plan` and `featureFailure()`'s "Upgrade to a paid plan for this feature." as `feature_needs_pro_or_enterprise`, in every toast (`ToastHost`, so the login screen's too) and the save-failed banner. Off the store the server's text stands.
- **Settings search.** `change_plan` is offered only where the Plan tab draws its card (`changePlanCardShown`, `SettingsSearchScope.showsChangePlan`).
- **No server text about the plan.** Where purchases are withheld, the server's `limit_clients` message (shown before when the app does not know the cap) never reaches the screen: the client form's banner, its save-failed banner (`EntityEditScreenScaffold.presentFieldErrors`), the inline-create dialog and the outbox's client rows all say `neutralClientLimitMessage` instead ("You have used all 5 clients on the Free plan.", or `free_plan_client_limit_hit` without a count), through `presentClientFieldErrors`. The other plan refusals the server words (`upgrade_to_view_reports`) are already mapped to the app's own string (`ReportErrorKind.planRequired`), and `limit_users` / `company_limit_reached` name a limit without asking anyone to buy.
- **The route.** `resolveUpgradeRoute(purchasesOffered:)` is required: on a store build without the offer it answers `storeSubscriptions` for an active store plan (never the Legacy Play replacement) and `planScreen` for everyone else, so a stray Upgrade can only reach the Plan tab, which offers nothing.

When the hosted service switches purchases on (`NINJA_IAP_PURCHASES_ENABLED`, or an account in `sandbox_account_keys` for App Review), the next ask answers yes and every surface is as before: the purchase sheet, Restore, "Upgrade" copy. Nothing in the app changes for that.

Tests: `test/domain/upgrade/upgrade_route_test.dart` (a store build launches without purchases), `purchase_delivery_test.dart` (purchase offer), `plan_hosted_actions_test.dart`, `plan_gate_copy_test.dart`, `test/ui/features/store_purchases_withheld_test.dart` (each surface in both states, and unchanged on desktop).

## A store plan is sold over only when the config says it replaces a Legacy Play subscription

An account with an active in-app plan (`hasActiveIapPlan`) is sent to the store's subscription management, never the purchase sheet, with one exception: a Legacy-app (`com.invoiceninja.app`) Google Play subscriber, whom the hosted service offers a new-app purchase. Once that purchase is applied, the server revokes the Legacy subscription with a prorated refund, and the sheet says so (`store_legacy_play_replaced_on_subscribe`, above the plans, and on the Plan card: if you subscribe here the Legacy subscription is cancelled for you and its unused time refunded, nothing to cancel yourself). On the Plan card the two buttons say what each does: **Choose a plan in this app** (filled) and **Manage in Google Play**, not "Manage Plan" beside "Manage subscription"; the card offers nothing (a progress line) while the config is asked, rather than Manage subscription that swaps for the offer under the user's finger; and the button spins while an Upgrade decides (`upgradeBusy`, up to `kUpgradeConfigTimeout`). An Upgrade that ends at the store's subscription page (`storeSubscriptions`, or the sheet's `activeStorePlan` refusal) says `plan_billed_in_app_store` first, so the app does not just switch away. `resolveUpgradeRoute` answers `legacyPlayReplacement` only when `offersLegacyPlayReplacement` holds:

- the build sells through Play (`storeOfBuild == PurchaseStore.googlePlay`). Never on Apple: a Legacy App Store subscriber changes level inside the Legacy app's subscription group, and the server never replaces one;
- the config says exactly `replaces_v1_play: true` (`IapConfig.replacesLegacyPlay`), and sells to the active account (`IapConfig.sellsTo`: enabled, a UUID token, the active account's `account_key`);
- the owner of the active company, with an active in-app plan. A recently lapsed plan still gets `storeSubscriptionsEnded`.

`purchases_enabled: true` is not the signal. The server also answers it for a store link whose `plan_expires` has just passed while the session still reads the plan as paid (a store billing retry): read as an offer, that would sell a new-app subscriber a second subscription and tell them it cancels a Legacy one. With no config, or one that does not say so, the route stays `storeSubscriptions` (fails closed). `launchUpgrade` and the Plan card ask the config only for an owner's active plan on a Play build, and the sheet checks again: `PurchaseService.saleRefusal` answers `activeStorePlan` for a live store plan the purchase would not replace, and `buy()` refuses it.

The answer is about the plan the account had when it was asked. As soon as a purchase is applied (before `auth.refresh()`, whose snapshot keeps the same scope) `PurchaseDelivery` drops the offer from the kept answer (`_dropReplacement`: the account key and token stay, so the next delivery asks nothing); it forgets the answer outright (`_forgetConfig`) when the session's store-plan state changes (`_planStateOf`: `hasIapPlan`, `plan`, `plan_expires`) and on a resume. An answer still on the wire then (the resume after the Play dialog asks while the purchase is being posted) is never kept and comes back without `replacesLegacyPlay`. Upgrade asks the config only through `replacementConfigFor` (owner, Play build, active store plan), waits at most `kUpgradeConfigTimeout` and reads no answer as no, and `launchUpgrade` runs one at a time, so a second tap while it waits does nothing.

Tests: `test/domain/upgrade/upgrade_route_test.dart` (Legacy Play replacement), `purchase_service_test.dart` (a live store plan), `upgrade_sheet_test.dart`, `upgrade_launcher_owner_test.dart` (replacementConfigFor), `purchase_delivery_test.dart` (the config after the plan changes), `plan_hosted_actions_test.dart` (a Legacy Play subscriber).

## Nothing is posted or finished until the config answers 200

`PurchaseDelivery` (built by `Services` on a store build only, and started at app launch so StoreKit hands over `Transaction.updates`) owns the hosted config, `GET kIapConfigPath`. It asks once per signed-in user and active company (base URL, user id and company id, `_scopeOf`): the server answers for the company of the token it is asked with (`InAppPurchaseController::show` checks that the user owns that company and that it belongs to the user's own account before it names `account_key`), so a switch to another company asks afresh and sweeps again, re-posting a refusal left with the store too. It keeps any 200, one without `account_key` included, and asks again after any failure, after a sign-out, on a company switch and when the app returns to the foreground. The purchase sheet (`PurchaseService.loadConfig`) reads the same answer: there is no second request.

Until that answer is a 200 with an `account_key`, nothing paid is posted and nothing is finished with the store. A 404 (a server without the route), a 5xx or no network leaves every purchase unfinished, said as `retryLater`, and tried again on the backoff. A 200 without `account_key` (a non-owner, a company of another account) leaves it unfinished and said as `retryLater` too, but with no retry timer: the same company would give the same answer, so it waits for a company switch, a sign-in or a return to the foreground. `purchases_enabled` gates only the sale (the sheet fails closed without it, a UUID `app_account_token` and an `account_key`); a purchase already paid for is always delivered, and Restore is never gated.

Before posting, a purchase is skipped, left unfinished and said as `retryLater`, when its own account token (Apple's `appAccountToken`, Play's `obfuscatedAccountId`, read from the store's transaction JSON) and the config's `app_account_token` are both set and differ: it was bought for another account on the same store account. A config with no usable token skips nothing (the server checks the token, `token_mismatch`), or a renewal would never be delivered. A revoked or upgraded-away Apple transaction is finished without a post and without a word. A purchase with no transaction id is never posted (the endpoint requires `inapp_transaction_id`) and never finished: a Play purchase with no order id yet is left as `retryLater`, logged once, and Play refunds it if it never gets one.

## A transaction is posted until it is answered, and never after

Each transaction is named by its own id (`_transactionKey`: Apple's transaction id, Play's order id), never the original id a renewal shares. Once the hosted service has answered it for good (200, or a final refusal on Apple) only finishing it is left: a failed Play acknowledgement retries the acknowledgement alone, on the growing backoff (the counter resets only once the store confirms a finish), and a resume sweep that read the store's list before the purchase stream's delivery finished it posts nothing. Closing the StoreKit / Play sheet resumes the app, so that race happens on every purchase. One refused but left with the store (every Google refusal, an Apple one with a non-final reason) is remembered per signed-in user: a resume or retry sweep skips it, a new sign-in's sweep (a launch included) and Restore post it again quietly, and the refusal is said once per user (in memory, so once more after a cold start).

A purchase not applied yet is swept again while the app runs, after 30 seconds, 2 minutes, then every 10 minutes (`kPurchaseRetryBackoff`), and on every return to the foreground (`PurchaseResumeObserver`). A Google acknowledgement Play did not confirm (`StoreBilling.completePurchase` answers false) is logged and swept again.

Tests: `test/domain/upgrade/purchase_delivery_test.dart`.

## Which answers finish a purchase

`POST kSubscriptionPath`:

| Answer | Apple | Google |
|---|---|---|
| 200 | finished, then `auth.refresh()` | acknowledged, then `auth.refresh()` |
| 409 / 422 with a final `reason` (`kFinalRejectionReasons`: `sandbox`, `expired`, `revoked`, `upgraded`, `linked`, `family_shared`) | finished, the server's message shown | left unacknowledged, so Play refunds it |
| 409 / 422 with any other `reason` (`account`, `token_mismatch`, `no_token`, `unverified`) or none | left unfinished, the message shown | left unacknowledged |
| 403, 429, 5xx, a 400 entity-missing, no network | left unfinished and tried again | left unacknowledged and tried again |

Finished too early, a purchase the account never got is gone: StoreKit never hands back a finished transaction, and Play never refunds an acknowledged one.

## The delivery key is the config's account_key

Every delivery posts `key` = the config's `account_key`, exactly: the account the hosted service applies the user's purchases to. The session's account keys are never used for it (`AuthSession.userAccountKey` names only the realtime channel). The sheet sells only when that key is the active company's account key (`IapConfig.sellsTo`); with a company of another account active it says plans are applied to the user's own account and opens no store sheet (`SaleRefusal.otherAccount`). A session with a blank account key (a cache from before 5.1.14) does not know its account yet: it says in-app purchases aren't available yet (`SaleRefusal.unavailable`) and sells nothing, rather than telling the owner to switch away from their own account.

## Where the translations live

The purchase copy is app-local, in `assets/i18n/_app_pending.json` (`store_*`, the withheld lines `free_plan_client_limit_hit`, `feature_needs_pro_or_enterprise`, `reports_need_pro_or_enterprise`, `docuninja_needs_pro_or_enterprise`, `free_plan_company_limit_reached`, `store_subscription_ended_info` and the `free_plan_*_info` client-limit lines, including `store_legacy_play_replaced_on_subscribe`, `choose_plan_in_app`, `manage_in_google_play`, `plan_billed_in_app_store`, `plan_managed_on_web`, `in_app_purchases_unavailable`, `restore_purchases_help`), with each shipped locale's translation in `_app_pending_<locale>.json` (docs/translated-string-rendering.md). A store's own name appears only in the copy for that store's build (`storeOfBuild`): App Review rejects a build that names another platform's store.
